# ふくおかポーカーナビ（福岡ポーカートーナメント日程アグリゲーター）

福岡県内のアミューズメントポーカー店のトーナメント日程を一括表示する公開サイト。
エースハイ合同会社の収益プロジェクト v1。

> **自動取込みの残存リスクを判断する人へ**: 本README末尾の
> **「リスク台帳（#1〜#22 一覧・cron有効化の判断材料）」** に、番号のついた項目の
> 状態（解消済み / 明示的に受容 / 未了・cron阻害 / 未了・阻害しない）が1枚にまとまっている。
> **個別の節を読む前にそこを見ること。**

## これは何か / 収益設計

- **資産になる「サイト」を母艦**にする（SEO：「福岡 ポーカー トーナメント 日程」等）。
- **LINE公式 / X**は無料の通知・回遊チャネルとして**サイトへ送客**（収益はサイト側）。
- 収益スロットは3層を最初から埋め込み済み：
  1. **広告（AdSense）** … `.adslot` の位置。PVが付けば自動で回る。
  2. **店舗のPR/有料掲載** … `venue.featured = true` でカード上部固定＋「PR」バッジ＋★。単価が高い本命。
  3. **周辺商品アフィリ** … 記事/サイドに随時追加（今後）。

### 自社広告カード（ポーカートナメ成績表）の3か所

AdSense/PR枠が埋まるまでの間、自社アプリの導線を3か所に置いている。**それぞれ狙いと太さが違う**ので、
1か所を触るときに他をつられて変えないこと。

| 場所 | セレクタ | 高さ(375px) | 備考 |
|---|---|---|---|
| トップ（大型バナーの**上**） | `.adslot .adCard` | 約100px | **位置は変えない**（社長判断。バナー下への移動案は却下済み）。上に積み上がる要素なので**意図的に薄くしてある**（社長指示・2026-07-29。元は約200px） |
| ページ下部 | `main > .adCard` | 約206px | 読み終わり地点なのでフルサイズのまま |
| 画面下固定 | `.stickyAd` | 約57px | 全ページ共通の常時表示 |

トップだけを薄くするために CSS を `.adslot` 配下に限定している。`.adCard` の共通ルールを直接いじると
下部カードまで薄くなるので注意。

薄くするのは**寸法（余白・画像・ボタン）を詰めて**行うこと。
トップは最も露出の多い枠なので、**「buyin・順位・収支を記録できる」という"何ができるアプリか"の訴求は文言から落とさない**
（高さ稼ぎに説明文を削ると CTR に直接効く）。320px級で見出しが3行に折り返す場合も、文言ではなく
`@media(max-width:360px)` 側の寸法で吸収する。

### `data.js` を更新したら（月次の日程入力のあと・店舗を追加したあと）

```
node tools/validate-data.js .            # data.js 自体の検査（日付書式・件数・id重複・構文）
node tools/gen-venue-pages.js .          # 店舗ページ35枚 + トップの店舗リンク行 + sitemap.xml
```

をリポジトリのルートで実行し、**生成物もコミットする**（GitHub Pages は静的配信なので生成物が必要）。
ズレていないかだけ見たいときは `--check` を付ける（書き込まず、一致しなければ非ゼロ終了）。
`validate-data.js` は日次ワークフローが使っているものと同じ検査で、**日付を `2026-9-5` のように書いてしまった**ときに
「どの店のどの大会か」まで出して止まる（再生成の失敗より先に、原因の側で止まる）。

> **人が `data.js` を触ったときの話**。日次の自動取込（Waitinglist / Instagram監視）で `data.js` が
> 変わったぶんは、それぞれのワークフローが同じジョブの中で再生成するので手作業は要らない。

- 店舗ページの日程は**「生成時の静的レンダリング＋閲覧時に `data.js` から再描画」のハイブリッド**。
  そのため再生成を忘れても**閲覧者には最新が出る**が、**JSを実行しないクローラには古い日程が見えたまま**になる。
  「画面で見えているから大丈夫」は成り立たないので、`--check` で機械的に確認すること。
- 静的側に焼き込むのは「実行日から先」ではなく **`data.js` に載っている期間そのもの**。
  実行日に依存させると、データを1文字も触っていないのに翌日には `--check` が落ちて検査が信用できなくなるため。
- **焼き込む期間は店舗ごとに決まる**（`tools/venue-schedule.js` の `venueRange()`）。
  日付つきトーナメントを持つ店では、その店の日付の範囲を月単位に丸めたものを使うので、
  **ある店に1件足しても他店のページは1バイトも変わらず**、見出しの「〇月〜〇月の掲載分です」も
  その店の実データと一致する。テストは `node tools/venue-schedule.test.js`。
  - 以前は data.js 全体の最小日〜最大日を全店で共有していたため、1店に1件足しただけで35ページが書き換わり、
    9月分を持つのが1店だけでも他34店に「7月〜9月の掲載分です」と出て9月の定期開催行まで焼き込まれていた
  - **定期開催（`RECURRING`）しか無い店**（現在 v5 / v41 の2店。v19 は2026-07-31にWaitinglistの
    自動取込対象になり、日付つきトーナメントが入ったのでこの分岐から外れた）はその店由来の日付が
    無いので、代表として
    「サイト全体の掲載期間の**先頭**1ヶ月」を展開して焼く（毎週繰り返すので1ヶ月あれば全曜日が出揃う）。
    最終月側に置かないのは、**その店と何の関係も無い遠い未来の月**（どこかの店に2027年3月の大会が
    1件載れば2027年3月）が並んでしまい、かつ他店の最遠日が動くたびにこの2店も書き換わるため
    - ⚠ **該当店の一覧は自動で追随しない。** ある店が自動取込の対象になると黙って該当から外れるので、
      `STORES` を増やしたらこの記述も見直すこと。実際の該当店は
      `VENUES.filter(v => venueRange(T, R, v.id)?.recurringOnly)` で数えられる
    - ⚠ **この2店については「他店の変更が波及しない」は構造的な保証ではない。**
      期間はサイト全体の最古月から決まるので、そこが動けば一緒に動く。実際に動かないのは
      「Waitinglist の日次取込が今日以降しか作らず、過去日のエントリに一切触れない」という
      **別の性質に依存**しているだけ。取込の仕様を変えるときはここも見直すこと
    - ⚠ **起点は放っておくと永久に動かず、焼き込まれる月は古びていく（自己修復しない）。**
      そのためこの2店の見出しは日付を断定しない文言にしてある
      （`トーナメント日程（毎週の定期開催）` ＋「1ヶ月ぶん（2026年7月）日付に展開した例で、
      特定の月の開催予定を示すものではありません」）。**時間が経つと嘘になる断定を書かないこと。**
      古い月が並ぶこと自体を解消したい場合は、焼き込みの下限日を入れる等の別の手当てが要る
  - **日付つきも定期開催も無い店**は期間そのものを出さない（見出しは「トーナメント日程」だけ）。
    1行も載っていないのに「この一覧は〇月〜〇月の掲載分です」と書くのは事実と合わないため
  - 日付は `YYYY-MM-DD`（ゼロ埋め）で書くこと。並べ替えを文字列の辞書順で行っているため、
    `2026-9-5` のような書き方が1件混ざると期間が逆転する。`monthRange()` はそれを検出して落ちる
- **閉店・掲載終了で `VENUES` から店を削除したときも、必ず再生成する。**
  再生成すると `data.js` に無くなった `venues/<slug>/` は**削除される**（対象名を表示する）。
  消さないと、閉店店舗の `LocalBusiness` 構造化データ付きページが更新されないまま公開され続ける
  （sitemap から消えるだけではインデックスは落ちない）。`--check` は孤児が残っていると非ゼロ終了する。
  なお `index.html` 以外のファイルを手で置いたディレクトリは自動削除せず、名前を出して止まる。
- イベントデータ（`jopt-data.js` / `big-events.js` 等）を変えたときは `node tools/gen-event-pages.js .` も実行する。

### `sitemap.xml` の所有者

`sitemap.xml` に載るURLは **`big-events.js`（イベントページ）と `data.js`（店舗ページ）の2つ**にまたがる。
両方の生成スクリプトがそれぞれ自前で組み立てると「後に実行したほうが相手のURLを消す」奪い合いになるため、
**中身を決める場所は `tools/gen-sitemap.js` だけ**にしてある。
`gen-event-pages.js` と `gen-venue-pages.js` は `sitemapFile()` を呼んで返ってきた文字列をそのまま書くだけで、1行も組み立てない。

- 入力が同じなら出力は同じ文字列なので、**どちらをどの順に何回実行しても内容は変わらない**
- **片方を実行し忘れてsitemapが古くなることもない**（どちらを実行しても全URLが揃う）
- `changefreq` / `priority` は**日付で変えない**。終了した大会を低優先度に落とす分岐を入れると
  「データを触っていないのに翌日 `--check` が落ちる」ことになるため。この2項目はクローラへの弱いヒントに過ぎない

### 定期開催（`RECURRING`）と自動取込の重複をどう消しているか

店の予約システムから自動取込んだ日程（`source:'auto'`）と、こちらが手で登録した毎週固定の定期開催（`RECURRING`）は、
**同じ大会を指していることがある**。両方を並べると同じ枠が2行になる。

```
 8月2日（日）
    16:10  2000 Turbo      ターボ  ¥2,000  30,000点   ← 自動取込
    16:10  Turbo 毎週日曜  ターボ  ¥2,000  30,000点   ← RECURRING
```

矛盾した情報ではない（時刻・参加費・スタックまで一致している）が、トップの一覧には「毎週◯曜」バッジが無く、
副文言（`+AO ¥1,000` / `STACK 30,000`）だけが食い違うため **「16:10開始の別大会が2つある」ように読める**。
「今月の開催数」も水増しされる。日程を正確に一覧できることが売りの媒体で、
**同じ大会が2行に見えるのは1行足りないより信用を損なう**（レビュー部の判断・2026-07-30）。

**規則**: その店の `source:'auto'` のエントリと **(`venueId`, `date`, 開始時刻) が完全に一致する** `RECURRING` の展開行だけを出さない。
残すのは必ず自動取込のほう（**店自身の予約システムが正**。名前が食い違う場合もAPI版を採用し、食い違いはログに残す）。

#### ⚠ 絶対に避けるべき実装

> **「自動取込の掲載期間まるごと `RECURRING` を止める」形にしてはいけない。**
> APIは**店が登録したぶんしか返さない**ため、登録が無い曜日の定期開催が全滅する。
> v19（CASINO Arrows 小倉店）で実測すると **28行 → 9行**になり、
> **土曜 Deep Stack 5回と月曜 Free Roll 5回が丸ごと消える**（品質管理部の実測・レビュー部が名指しで警告）。
> 必ず**一致した行だけ**を落とすこと。

規則をこれ以上広げないこと。特に次の2つは**触ってはいけない**（どちらも実在するデータで、消すと事実と食い違う）。

- **`source:'auto'` 以外の同時刻衝突**。例: v33 `2026-07-10 19:00` の `FPC AJPC DAY1`（¥0・`source:'semi'`）と、
  毎週金曜19:00の `JOPT福岡サテライト`（¥4,000）。**参加費が違う別の大会**である
- **開始時刻が `HH:MM` として読めない行**（空文字・`未定` 等）。例: v35 の5件（7/4・7/10・7/11・7/12・7/25）は
  `start` が**空文字どうし**。空文字を一致とみなすと無関係な大会が消える

#### なぜ独立した1ファイル（`recurring-dedupe.js`）なのか

`RECURRING` の展開は**2箇所**にあり、**生成するフィールドも元から違っていた**。

- `tools/venue-schedule.js` の `vpExpandRecurring()` … 静的な店舗ページ用
- `index.html` の `expandRecurring()` … トップのSPA用

同じ判定を2つ書けば必ず片方が古くなる（PR #15 が潰した不整合の再導入）。そこで**判定だけ**を素のJSファイルに切り出し、
**3つの実行環境が同じ1本のバイト列を読む**形にした。

| 実行環境 | 読み方 |
|---|---|
| Node（静的ページ生成・`hasSchedule`） | `tools/venue-schedule.js` が `require` |
| 店舗静的ページ（閲覧時の描き直し） | 生成HTMLの `<script src="/recurring-dedupe.js">` |
| トップのSPA | `index.html` の `<script src="recurring-dedupe.js">` |

**「共通化のためにどこかへ寄せよう」として壊さないこと。** 寄せられない理由は2つある。

- `tools/venue-schedule.js` に**戻せない**。あそこの `SCHEDULE_JS` は Node の `vm` で回す**文字列**で、`index.html` からは読めない
- `index.html` に**注入できない**。注入するとトップページが新たに「生成物」になり、生成ステップと `--check` がもう1本増える
  （現在 `gen-venue-pages.js` が `index.html` に触るのは `#venueLinks` の1行だけ、という不変条件も崩れる）

`data.js` / `big-events.js` と同じ「ブラウザからも Node からも読める素のJS」なのでリポジトリ直下に置いてある。
ES5で書いてあるのは、店舗ページに埋め込まれる `SCHEDULE_JS` と同水準に合わせるため。

#### 実装上の注意

- **SPA側の間引きは `expandRecurring()` の出口1箇所**で行う。消費点は4つ
  （`ALL_TOURNAMENTS` / `monthTournaments()` / `thisMonthCount` / 店舗モーダル）あり、
  消費点ごとに書くと**足し忘れた1つだけ重複が残る**
- **展開行は必ず `venueId` を持たせる**。判定は `venueId` を鍵に使うので、欠けると
  **例外も出さずに黙って空振りする**（実際、静的側の `vpExpandRecurring()` は元々 `venueId` を持っておらず、
  この形にした初回は静的側だけ無反応だった）。`recurring-dedupe.js` は `venueId` の無い行を見つけたら落ちる
- **`auto-import-stores.json` ではなくエントリの `source` で判定している**。ブラウザは JSON を同期的に読めず、
  店リストを `index.html` に写すと今度はデータ側でズレるため。`source:'auto'` を書くのは
  `tools/import-waitinglist.js` だけ（Instagram監視は `'semi'`）なので signal としては同じで、
  抑止される集合も変わらない。両者の食い違いは `auditAutoStores()` が生成時に照合して**警告だけ**出す
- 抑止した行の**件数と内訳**は `node tools/gen-venue-pages.js .` の標準出力（＝日次ジョブのログ）に出る。
  この間引きは「出力に何も現れないこと」で成功するので、ログが唯一の観測手段
- 壊れたときの挙動は**わざと非対称**にしてある。店舗静的ページは
  `recurring-dedupe.js` が読めなければ**描き直しを行わない**（生成時に間引き済みのHTMLが残る＝重複は復活しない）。
  トップのSPAは `console.error` を出して**重複したまま表示**する（一覧ごと真っ白にするより害が小さい）。
  同じ状況で生成側は**止まる**ので、異常は日次ジョブが検知する
- **SPA側が間引きを通していることはテストで固定してある**（`tools/recurring-dedupe.test.js` が
  `index.html` から `expandRecurring()` を切り出して実行し、返り値で確かめる）。
  文字列一致ではなく挙動で見ているのは、変数名を変えただけで落ちる／別の書き方に変えると通ってしまうのを避けるため。
  切り出しの目印は `const RECURRING_LIST =` 〜 `const addDays =` で、動かすとテストが明示的に落ちる

#### ⚠ テストに「実データの件数」を書かないこと

当初 `tools/recurring-dedupe.test.js` には「**現在の `data.js` では1行も抑止しない**」という検査を置いていた。
PR #23 の時点では正しかった（自動取込は v3 の1店だけで、その店に `RECURRING` が無かった）。
しかし翌日 v19 の自動取得を有効にした瞬間、日次の bot が9件を取込み、**設計どおり5行が間引かれて、
誰も何も間違えていないのにテストが赤くなった**。

`data.js` は無人の日次ジョブが毎日書き換える。そこに固定の件数を期待値として置くと、
**店を1つ足すたびに同じことが起きる**。テストが赤いまま放置される状態は
「赤いのが普通」という学習を生み、警報そのものの価値を壊す。

実データに対しては **いつ・どの店が自動取込に加わっても成り立つ性質**だけを見ること
（`tools/venue-schedule.test.js` が PR #15 で採った方針と同じ）。現在この間引きが実データに対して見ているのは:

- 自動取込が**無い**店の日程表は、間引きの有無で**1バイトも変わらない**
- 消えるのは「同じ枠に自動取込の実体がある定期開催」**だけ**（消えた行ごとに相手の実在を確認する）
- **日付＋開始時刻の枠は1つも減らない**（行は減ってよいが、枠が消えるのは開催が消えたことになる）
- 間引きで掲載0件になる店は無い（sitemap の掲載判定が変わらない）
- 抑止した行数と記録した件数が一致する／抑止が起きるのは `auto-import-stores.json` に載っている店だけ

固定の件数を見たい検査は、実データではなく**テスト内の固定フィクスチャ**に対して書く。

#### 既知の見え方（改善候補・2026-07-31時点は対応しない）

抑止された枠では、`RECURRING` 側が持っていた **「毎週◯曜」バッジが消える**（残るのは自動取込の行で、
そちらは日付つきの単発として登録されているため）。同じ週次大会でも、
**APIに登録のある週はバッジ無し・登録の無い週はバッジ有り**、という並びになる。

誤りではない（どちらも実際の開催で、時刻・参加費・スタックは正しい）ので今回は手を入れていない。
気になる場合の改善候補は「**抑止するときに、残す側へ `recurring` の印だけ引き継ぐ**」。
名前は引き継がないこと（店自身の予約システムが正なので、名前はAPI版のままにする）。

## 大型イベントの追加手順と掲載期間ルール

大型大会（WJPT / JOPT / FST など）は**基本的にWJPTと同じ掲載の仕方をする**（社長の恒久ルール）。
つまり **トップページのバナー ＋ サイト内の専用ページ（`#<id>`）** の2点セットで載せる。

### 掲載期間ルール（社長指示・2026-07-29）

判定は `big-events.js` に**一本化**されており、日付比較を各所に書き足してはいけない。

- **掲載開始日 = そのイベントの初日 − 14日**
- **掲載終了日 = そのイベントの最終日 + 1日**（その日は含む）
  - 大型大会は日付を跨いで進行することがあるため、最終日の翌日までは載せ続ける
- 各イベントの掲載ウィンドウは**他のイベントを一切参照せず独立**して決まる。したがって
  **掲載期間は重なってよく、トップのバナーは同時に複数件出る**（社長了承済み）
- 逆に、どのウィンドウにも入らない期間は**バナー0件**になる（現在の登録内容だと 2026-08-18〜09-04）。
  これは仕様であってバグではない。埋めようとしないこと

> **【重要】掲載ウィンドウと「開催中/終了」の判定は、しきい値が意図的に1日ずれている。**
> 掲載ウィンドウは *最終日+1* まで、開催中/終了の判定（`isEventArchived()`）は *最終日* まで。
> つまり**最終日の翌日は「バナーは出るが、終了状態（暗転＋「終了」バッジ）で表示される」**のが正解。
> 社長の言葉:「掲載してほしいだけで次の日はバナーは終了でいいです」。**揃えないこと。**

現在の登録内容だと掲載期間はこうなる：

| 大会 | 会期 | 掲載開始（初日−14日） | 掲載終了（最終日+1） |
|---|---|---|---|
| WJPT | 2026-07-18〜07-20 | 2026-07-04 | 2026-07-21 |
| JOPT | 2026-07-30〜08-02 | 2026-07-16 | 2026-08-03 |
| NIPPON SERIES | 2026-08-11〜08-16 | 2026-07-28 | 2026-08-17 |
| FST 5.0 | 2026-09-19〜09-23 | 2026-09-05 | 2026-09-24 |

### どこに何が出るか

| 場所 | 何件 | 判定関数 |
|---|---|---|
| トップのバナー | 掲載ウィンドウに入っているもの**全件**（0〜複数）。並びは 開催中 → まもなく（初日の近い順） → 終了 | `visibleBigEvents()` |
| フッターの「大会特集」 | **1件**。開催中があればそれ（複数なら最終日が早い方）、無ければ次の大会（初日が最も近い未来）。どちらも無ければ行ごと非表示 | `footerBigEvent()` |
| 大型一覧（`#majors`） | 未開催・開催中は全件、終了済みは**新しい順に3件まで**（暗転表示）。それより古い大会は出さない | `bigEventListForIndex()` |

**フッターは掲載ウィンドウに縛られない**（バナー0件の期間でも「次の大会」を出し続ける）ため、
バナーとフッターが一致しない日がある。これも仕様。
静的ページ（`events/<slug>/`）のフッターも同じ `big-events.js` をブラウザ側で実行して判定するため、
ページを再生成しなくても掲載中の大会が自動で切り替わる（生成時に焼き込まない）。

#### フッターは「恒久リンク行」と「大会特集」の2本立て（消さないこと）

**トップページ（`index.html`）と静的ページ（`events/<slug>/`）の両方**のフッターに、
**役割の違う2行**が入っている。**片方を理由にもう片方を消さないこと。**

| 行 | 中身 | 目的 |
|---|---|---|
| 恒久リンク行 | レジストリの**全大会**（会期の古い順） | **SEO**。静的イベントページへのクロール経路・内部リンク評価。**日付で消えてはいけない** |
| 大会特集 | **その日の1件**（`footerBigEvent()`） | 回遊。該当が無ければ行ごと非表示 |

リンク先は各エントリの `featureUrl`。静的ページを持つ大会はその静的URL、
持たない大会（FSTなど）はハッシュURL（`/#fst`）になる。

恒久リンク行は**トップも静的ページも `tools/gen-event-pages.js` が生成する**（**どちらもJSなしのHTMLに
実リンクが載る**のが要点）。出どころは `permanentEventLinks()` ただ1つで、**手で書き足す場所はない**:

| ページ | 生成方法 | レジストリに足したとき |
|---|---|---|
| `events/<slug>/` | `permanentEventLinks()` がページ全体と一緒に焼き込む。自分自身は `aria-current="page"` でリンクにしない | **生成スクリプトの再実行だけ**で増える |
| `index.html`（トップ） | 同じ `permanentEventLinks()` が **`<div id="evtLinks">…</div>` の1行だけを上書き**する（`index.html` の他の箇所には触らない）。実行時には `mountBigEventLinks()` が同じ内容で描き直す | **生成スクリプトの再実行だけ**で増える |

**ズレを検知する仕組み（覚えておく必要をなくすため、3重にしてある）**

| 仕組み | いつ効くか | 何が起きるか |
|---|---|---|
| `node tools/gen-event-pages.js <repo>` | 大会を追加したとき | トップと静的ページの**両方**が同時に更新される（片方だけ、が起こらない） |
| `node tools/gen-event-pages.js <repo> --check` | レビュー時（手動） | 書き込まずに突き合わせ、1文字でも違えば**非ゼロ終了**して落とす |
| `mountBigEventLinks()` の自己点検 | ブラウザで開いたとき（初回描画時） | HTMLの静的リンクがレジストリとズレていたら**コンソールに警告**を出す |

> 過去に「大会特集は1件」という指示を取り違えて恒久リンク行ごと削ってしまい、
> 全大会が終了した日以降に内部リンクがゼロになる状態を作ってしまったことがある
> （静的ページ側・トップ側で2回）。「1件」なのは**大会特集の行だけ**であって、内部リンクの話ではない。
> さらにその直後、**静的ページだけ直してトップを見落とす**という取りこぼしも起きた。
> ズレていても `mountBigEventLinks()` が描き直すので**画面上は正常に見え、目視では気づけない**
> （欠けるのはJSを実行しないクローラに対してだけ）。上表の仕組みはこの見えない壊れ方への対策。

**PR/pushに対するCIは現時点で未実装。** ただし日次の自動取込ワークフロー2本
（`import-waitinglist.yml` / `monitor-instagram-apify.yml`）だけは、自分がpushするツリーに対して
`node tools/validate-data.js .` と `node tools/gen-venue-pages.js . --check` を実行している
（人の変更に対する `--check` は依然として手で走らせる）。将来CIを組む担当への注意が2点ある。

1. **`<repo>` は相対パス（`.` など）でも絶対パスでも動く。** 3つの生成スクリプトはいずれも
   受け取ったパスを `path.resolve()` で絶対パスに直してから `require()` する。
   ```sh
   node tools/gen-event-pages.js . --check                      # ← 相対パスでも動く
   node tools/gen-event-pages.js "$GITHUB_WORKSPACE" --check    # ← 絶対パスでも動く
   ```

### トップのバナーの見せ方（社長指示・2026-07-29）

掲載が複数件になっても**縦には積まない**。縦積みだとバナー1件につき約195px、直下の
「トーナメント日程」見出しが押し下げられ、ファーストビューから日程が消えてしまうため。

| 件数 | 見せ方 |
|---|---|
| 0件 | 領域ごと非表示（`#bigEventBanner:empty`） |
| 1件 | バナー1枚。**カルーセルUI（ドット・矢印）は出さない** |
| 2件以上 | **横スライド（カルーセル）**。縦の占有は常にバナー1枚分 |

実装は `index.html` の `renderBigEventBanner()` / `initBigEventCarousel()`（CSSは `.evtCarousel` 系）。
**外部ライブラリは使わない**（このサイトは依存ゼロで動いている）。ネイティブの横スクロール＋
CSS `scroll-snap` だけで作ってあり、レジストリに大会を足せば枚数は自動で増える。

「スライドできる」と伝えるための仕掛けは次の4点セット。**どれか1つを外すと伝わらなくなるので削らないこと**。

1. **次の1枚の端をちら見せ（peek）** — スライド幅を `86%` にして右に次が覗く（375px幅で約38px）。最重要。
   ただし**スライドが必要なときだけ**の仕掛けで、全部が一度に収まる幅（下記）では peek は無くなる
2. **ドットインジケーター** — 枚数と現在位置。現在のドットは横長のバー状に強調
3. **左右の矢印ボタン** — `min-width:720px` かつスクロールが必要なときだけ表示（タッチ環境はスワイプが自然なので補助扱い）
4. **初回のヒントアニメーション** — 一瞬だけ横に動いて戻る。`prefers-reduced-motion: reduce` では**必ず無効**

#### 720px以上では「スライド」ではなく「横並び」になる（2件のとき）

バナー画像は 1024×412（約2.5:1）なので、**スライドを横に広げるほど縦に伸びる**。幅いっぱいまで
伸ばすと1枚で高さ390px前後になり、直下の「トーナメント日程」見出しがファーストビューから外れる。
そこで **720px以上ではスライド幅に上限を掛けて**、2枚が横に並ぶようにしている。

| 幅 | スライド幅の上限 | 実測（2件時・スライド幅 / バナー領域の高さ / 見出しY） |
|---|---|---|
| 〜719px（モバイル） | なし（`flex:0 0 86%`） | 375px: 295px / 191.7px / **669** |
| 720〜999px | `calc((100% - var(--ec-gap)) / 2)` | 768px: 363px / 201.0px / **637**　999px: 478.5px / 247.5px / **683** |
| 1000px〜 | `470px`（トラック幅は常に968px） | 1280px: 470px / 244.1px / **680** |

- `--ec-gap` は `.evtCarousel` に置いたスライド間の余白（10px）。**gapの数字を2箇所に書かない**ための変数
- 全部収まると JSが `.ec-fits` を付け、**矢印とドットを消す**（動かないのに操作UIがあると誤解を招くため）
- 3件以上に増えれば収まらなくなり、**自動でスライド表示に戻る**（判定は `track.scrollWidth <= clientWidth` の実測。枚数や画面幅を決め打ちしない）

> **この上限は「2枚が丸ごと収まる幅になる値」でだけ掛けること。**
> 中途半端な固定値（例: 520px）で掛けると、2枚目が大きく覗くのに最後まで見えず、
> **「日程を見る →」ピルが縦に真っ二つ**になる。実際に一度その状態でレビューに出して差し戻された。
> 720〜999pxを `calc((100% - gap) / 2)` という**相対値**にしているのはこのため
> ―― 2枚＋gapがトラック幅に必ず一致するので、「途中で切れる幅」が原理的に発生しない。
> 変更したら **320〜1960pxを1px刻みでスイープし、CTAの部分表示がゼロ**であることを実測で確認する。

> **モバイル（〜719px）には手を入れないこと。** 画面が狭く2枚を並べる余地がないうえ、
> 見出しYの現行値（320px=469/640/642、375px=477/670/669、390px=477/676/674、414px=477/686/682。
> それぞれ0件/1件/2件）が社長・レビュー確認済みの基準になっている。

**やってはいけないこと**

- **自動スライド（オートプレイ）を足すこと。** トップの自動スクロールはコミット `6f9eddb` で意図的に廃止済み
- **ページ全体に横スクロールを出すこと。** 横に流れるのは `.ec-track` の内側だけ（320px / 375px で
  `document.scrollWidth === clientWidth` を必ず確認する）
- **大型一覧（`#majors`）を横スライドにすること。** あちらは一覧なので縦並びのままが正しい

### Waitinglist 自動取込（`tools/import-waitinglist.js`）

DMMポーカーのイベントカレンダーは Waitinglist の埋め込みで、その裏に**認証不要の公開JSON API**がある。
これを使って掲載店のトーナメント日程を毎日自動取得する。**手入力ゼロで日程が最新化される唯一の経路**。

```
GET https://api.waitinglist-poker.com/v1/game-schedules/tournament?storeId=<storeId>&limit=100&page=1
    User-Agent: fukuokapoker.com-bot/1.0 (+https://fukuokapoker.com/contact.html)
→ { totalRecords, tournaments: [...] }   ※limit最大100・pageは1始まり。ページ間は1秒あける
```

- **取得のマナー（方針）**: **ブラウザを詐称しない。** 実体は GitHub Actions から1日1回動く当サイトのボットなので、そのとおり名乗り、問い合わせ先（`contact.html`）をUAに含める。相手側が「これは何者か」を確認して、遮断したい・連絡したいと思ったときにそれができる状態にしておくため。
  - 調査時は `Origin: https://poker.dmm.com` / `Referer: https://poker.dmm.com/` とブラウザのUAを付けて叩いていたが、**外しても同じ HTTP 200 で同じ件数が返る**ことを確認したうえで削除した（2026-07-31検証）。認証もトークンも不要な公開エンドポイントで、`api.waitinglist-poker.com` と `poker.dmm.com` のどちらにも `robots.txt` は存在しない（404）
  - 1日1回・ページ間1秒・対象1店舗（105件を2リクエスト）で、相手の負荷は無視できる範囲に収めている
- **実行**: GitHub Actions `.github/workflows/import-waitinglist.yml` が**毎日 06:23 JST**（cronは `23 21 * * *` UTC）に実行。手動実行（`workflow_dispatch`）も可。差分があるときだけ `github-actions[bot]` がコミット＆プッシュする（push直前に `git pull --rebase` して、checkout〜pushの間に main が進んでも静かに止まらないようにしている。この `git pull --rebase` がマージベースを解決できるよう、`actions/checkout` は `fetch-depth: 0`＝浅いクローンにしない）
- **対象店舗**: スクリプト冒頭の `STORES` 配列で管理。**1行足すだけで店舗を増やせる**。現在有効なのは `v3` と `v19` の2店（他はコメントで控えてある）

  - **引き継ぎ元は「機械が所有する同じ `id` の既存」1件だけ**（2026-08-04〜）。**人の行から引き継ぐ経路はもう存在しない** — 人の行の枠にはAPIの行を書かないので、人の行のGTD・タグは**その行がそのまま残ることで守られる**
  - ~~**同じ (date, start) にAPI側が複数あるとき**は、どの大会の情報か特定できないため**名前が一致する手入力からのみ**引き継ぐ（一致しなければ引き継がない）。見送った件数は実行ログに出る~~
    → **2026-08-04にやめた。この機構（`usableManuals` / `stats.ambiguous`）はコードごと削除してあり、この件数はログに出ない。**
    **★「名前が一致しないGTDは引き継がれない」という追加の安全策が今も働いている、と読まないこと。**
    - **旧判断（引き継ぎ先を特定できないなら、誤情報を出すより欠落させる方が軽い）は否定されていない。
      枠ごと書かない新規則に包含された** — 引き継ぎを見送るのではなく**機械の行そのものを書かない**ので、
      GTDが誤って配られる余地が**構造的に無くなった**（＝旧機構は到達不能になり、
      到達不能なカウンタは「鳴らない警報」なので消した）
    - **★ここを読んで「同じ枠なら機械を優先すればいい」と戻さないこと。** 欠落 > 誤情報 という優先順位は生きている
- **`pinnedTags`（人手で固定するタグ）**: **`pinnedTags` が必要なのは `ターボ / ディープ / PLO / ミックス` の4語だけ**。この4語は毎回APIの `feature`・`gameRule` で上書きされるため、`tags` に手で書いても翌日消える。人の判断でこの4語を足したいときは `pinnedTags` に入れる。`carryOver` が GTD・プライズと同じく引き継ぐため、毎日の再生成後も残る
  - **それ以外のタグ（`バウンティ` `特別開催` `サテライト` `大型` `フリーロール` `リーグ` など）は `tags` に直書きすれば保持される**。`pinnedTags` に入れる必要はない（入れても動くが、「APIと競合するので固定した」という意図が読めなくなるので使わないこと）
  - `tags` は毎回「API由来タグ ＋ 人手タグ ＋ `pinnedTags`」で組み立て直される（描画側は `tags` を見るだけでよく、変更は不要）

  ```js
  // 例: ｍ Hyper Deep Turbo（feature は「ターボ」だがスタック10万点で実質ディープ）
  { …, "tags": ["ターボ", "ディープ"], "pinnedTags": ["ディープ"] }
  ```

  空のときはキーごと出力しない（`lowConfidence` と同じ任意フィールド扱い）。
  **なぜ自動判定にしないか**: APIの `feature` は単一値で「ターボかつディープ」を表現できず、さらに欠測もある（`m WTB Turbo` は `feature` が無く、名前にTurboとあるのにターボが付かない）。`startingStack` からの推測も、ノーマルとディープの両方に 40,000 が出現するため閾値では分けられない。特定の大会に合わせたマジックナンバーは他店に広げた瞬間に破綻する。そこで**自動判定を増やさず、人が付けたことがデータ上わかる形**で残す設計にした
- **upsert規則**（データ喪失を起こさないための取り決め）
  1. **過去日（JST基準の今日より前）のエントリは一切触らない**
  2. **機械が所有する** `source: 'auto'` の今日以降のエントリは毎回作り直す（APIから消えた＝中止の場合はそのまま消える）。ただし上記のとおり人手情報は引き継ぐ
  3. 機械が所有する行のうち **人が直した項目**は、**その項目だけ**人の値を残す（行ごと凍結はしない。下記「人が入力した値を機械が壊さない仕組み」）

     - ~~手入力のうち API側に同じ (date, start) があるものはAPI版に置き換える~~ → **2026-08-04にやめた**。理由は下記
  5. それ以外の既存エントリ（API側に対応が無いもの）は残し、件数と内訳をログに出す（APIに未登録なのか中止されたのか人間が判断できるように）

- **安全弁**: 「HTTP 200が返ってきたから正常」とは扱わない。次のいずれかで**その店舗のデータを書き換えない**（ワークフローも失敗する）
  1. fetch失敗 / HTTP 200以外 / レスポンス形状が想定外
  2. 対象店舗の取得件数が **0件**
  3. **ページング不整合** … `totalRecords` に対して**重複排除後の**実取得件数が足りない（2ページ目が空で返る／同じidが水増しされている／ページング中のレコード挿入で同一レコードが2ページに跨る、等）。排除“前”の件数で判定すると、重複で嵩上げされたぶんだけ実データが静かに欠ける
  4. **別店舗の混入** … `store.displayId` が**無い**、または要求した `storeId` と違うレコードが1件でもある（フィールドが落ちているだけで検証がスキップされないよう、存在自体を必須にしている）
  5. **今日以降の件数の急減** … 部分障害（数件しか返らない・過去日しか返らない等）を検出する。**「前回の半分未満」（比率）と「1回で10件以上の減少」（絶対値）の両方**で見る。比率だけだと件数が多い店ほど1回で大量に消せてしまうため。閉店・長期休業など正当な減少のときは `--allow-shrink` を付けて人が明示的に通す
  6. 書き込み直前の自己チェック … 「取得に成功した店舗以外のデータが変化していないか」「過去日のエントリが増減・変化していないか」（`tools/schedule-write-guard.js`。Instagram監視と**同じモジュールを共有**している。過去日は**並び順だけ見ない** — 理由は下記「過去日の並び順について」）
  7. 書き込み直前の突き合わせ … 「**機械のものでない行が1つも書き換わっていないか**」「**人が直した項目が機械の値に戻っていないか**」（下記「人が入力した値を機械が壊さない仕組み」）

  **失敗の隔離は店舗単位**。1〜5 はその店の中で完結する異常なので、**失敗した店だけをスキップして他店は通常どおり取り込む**（6 は自分のバグを疑う検査なので全体を止める）。
  - **もとは「全店そろって成功しなければ1文字も書かない」だった。** 狙いは中途半端な書き込みを残さないことで、それ自体は今も正しい。ただし店ごとのデータは互いに独立していて、A店が失敗してもB店の結果は完全に整合しているため、「B店を書かない」ことが安全性に寄与していなかった。むしろ**毎月1日にAPIが翌月ぶんを返さない店が1つあるだけで、正常な他店の取込まで丸ごと止まる**という弊害のほうが大きい（実測: v3 の未来エントリが1件欠けた状態で v19 が0件を返すと、v3 は復活しないまま終わる）。そこで隔離の単位を「全店」から「1店」に変えた。店をまたいで中途半端になることは無い（店ごとに全件そろってから `mergeStore` に渡す）
  - **終了コード**: `0` = 全店成功 ／ `2` = 一部の店だけ失敗（**成功した店のぶんは書き込み済み**）／ `1` = 何も書いていない（全店失敗・`data.js` を読めない・自己チェックでバグを検出）
  - **ワークフローは `2` を素通しして、コミット・pushまで進めてから最後にジョブを失敗させる**。ここで止めると成功した店のぶんがコミットされず、隔離した意味が無くなるため。したがって**このジョブが赤い＝全部止まった、ではない**
  - **どの店が失敗したかは `::error::` 注記で実行サマリの先頭に出る**（ログを遡らなくてよい）。失敗店の一覧も取得ループの直後にまとめて出す
  - テスト: `node tools/import-waitinglist.test.js`（実際にプロセスを起動し、1店だけ壊した応答を与えて他店が通ることを確かめる）
  - **自己チェックの比較は「マージ前のディープコピー」と行う**。`before` と `arr` は同じ要素オブジェクトを共有するので、`before` をそのまま左辺にすると**エントリを in-place で書き換えるバグが両辺に同じように映って素通りする**（構造的な差し替えは検知できるが in-place は抜ける）。現在の `mergeStore` / `carryOver` は常に新しいオブジェクトを作るので実害は無いが、将来そういう実装が紛れ込んでも守られるようにしてある（テストで固定済み）

  ⚠ **毎月1日に「0件」で落ちることがある**。APIは**当月1日以降のレコードしか返さない**（2026-07-31に v3/v19/v22/v27/v33 の5店で確認。いずれも6月以前は0件）。対象店が翌月ぶんをまだ登録していない朝は `totalRecords=0` になり、上記2で**その店だけ**スキップされる（他店は通る）。店が潰れたわけではなく、多くは数日中に登録されて自然に復旧する。
  - **急減（上記5）と取り違えないこと**。前回件数と今回件数は同じ基準日で数えるため、開催日が過ぎるだけなら両方が同時に減って差は0にしかならず、急減ガードは発火しない（v19 の登録内容で 8/1〜8/31 の全日を通しても1度も鳴らない）。急減が実際に鳴るのは**店が未来の大会を取り消したとき**だけ。月初に赤くなったら急減ではなく0件を疑う
  - **他店は巻き添えにならない**（店舗単位の隔離。2026-07-31〜）。たとえば v19 が0件の朝でも **v3 は正常に更新されて push される**。ジョブは `rc=2` で赤くなるが、止まっているのは v19 だけ

  一時的なネットワークエラーは最大3回までリトライする。加えてワークフロー側でも、コミット前に `data.js` の**構文・件数（500件未満なら異常）・id重複・日付書式（`YYYY-MM-DD` のゼロ埋め・実在する日付か）**を `tools/validate-data.js` で検証する（`git pull --rebase` の後にもう一度、**押す物そのもの**を検証する）

- **確認用**: `node tools/import-waitinglist.js --dry-run` で書き込まずに差分サマリだけ出せる。実行時は必ず `追加 / 更新 / 変更なし / 削除 / 人の行を守って見送り / API未掲載の手入力` の件数を出力する（`--dry-run` は `data.js` も控えのJSONも書かない）
- **静的ページの再生成もこのワークフローの中でやる**: 自動取込で `data.js` が変わると、そのスナップショットである `venues/<slug>/index.html` と `sitemap.xml` が古くなる（閲覧者にはブラウザ側の描き直しで最新が出るので、**画面を見ても気づけない**）。そこで `import` → 妥当性確認 → コミット → `git pull --rebase` の**あと**に `node tools/gen-venue-pages.js .` と `--check` を実行し、生成物を同じコミットに `--amend` で取り込んでから push する。**自動取込ぶんについて人が再生成する作業は無い**。
  - **再生成を rebase の「後」にしている理由**: rebase は他のジョブ（Instagram監視）や人のコミットを取り込む。rebase の前に生成すると、取り込んだぶんの `data.js` が生成物に反映されないまま push され、**main が `--check` の通らない状態になる**（実測: 人が `data.js` だけを push した直後にこのジョブが走ると、その店のページが古いまま押される）。生成物をコミットに含めずに rebase することで、`venues/*.html` の衝突も避けられる（このコミットが持ち込むのは `data.js` だけになる）
  - **`--amend` する前に「自分のコミットがまだ有るか」を実測で取り直す**: 同じ変更を他のジョブや人が先に push していると、`git pull --rebase` で自分のコミットが**空になって捨てられる**。その状態で `--amend` すると**他人のコミットを書き換えてしまい**、push が `non-fast-forward` で拒否される（remote は無傷でジョブが落ちるだけだが、ログから真因に辿り着けない）。そこで rebase の直後に `git rev-list --count "@{u}..HEAD"` で数え直し、0 なら amend しない
  - **取込みに差分が無いのに生成物がズレていた場合**（人が `data.js` を触って再生成を忘れた等）も、このジョブが直して push する。ただし「Waitinglistから日程を自動取得」ではなく **`chore: 静的ページを data.js に追随させる（自動再生成）`** という別のメッセージでコミットする（取込みの手柄にすると監査ログが事実と違うものになるため）
  - 焼き込む期間が店舗別（`venueRange()`）になったので、**日次で書き換わるのは `data.js` と取込対象店のページだけ**。実測（v3に1件追加 / v3の9月分が消える / 2027年3月の大会が1件載る の3シナリオすべて）で**2ファイル**（`data.js` + `venues/m-holdem-nakasu/index.html`）に収まり、他店のページと `sitemap.xml` は動かない。**対象店を増やすとページの枚数もそのぶん増える**（`STORES` を触ったらこの記述も見直すこと）
    - ただし**定期開催しか無い2店（v5/v41）だけは構造的な保証ではない**。この取込が過去日を作らない・触らないので結果的に動かないだけで、依存関係がある（上記「`data.js` を更新したら」の⚠を参照）
  - 全店共通の期間だった頃は、同じ3シナリオが **2 / 36 / 36 ファイル**、`venues/` 全体が 1.1MB → 1.4MB（`casino-bar-leje-hakata` 単体で 61KB → 142KB）まで膨らんでいた。無人の日次pushでこれをやると `venues/` を触る他の作業と競合が常態化する
- **自動取得の対象店リストを出力する**: 実行のたびに `STORES` の内容を `auto-import-stores.json`（リポジトリ直下）に書き出す。**掲載管理コンソール（別リポジトリ `fukuoka-poker-admin`・ローカル専用）が読んで「この店は自動取得なので手入力不要」を出す**ためのもの。コンソール側がこのスクリプトの JavaScript をパースしなくて済むようにしてある。
  - 中身は `STORES` から取れる値だけで、**生成日時などの毎回変わる値は入れない**。入れると日程に変化が無い日でもこのファイルだけが差分になり、日次実行のたびに無意味なコミットが増える（ワークフローの差分判定は `git status --porcelain` なので1バイトでも変われば必ずコミットされる）
  - `STORES` を編集したら `node tools/import-waitinglist.js` を実行して**このファイルも一緒にコミットする**。忘れても翌朝の日次実行で更新される。`--dry-run` を付けると書き込まずに「ズレているか」だけを報告する
  - 途中で異常を検知して中止した実行では書き換えない（`data.js` と同じく、失敗した実行は何も残さない）
  - **公開ウェブルートに置いているのは意図的**（`https://fukuokapoker.com/auto-import-stores.json` として誰でも取得できる）。掲載管理コンソールは別リポジトリのローカル専用ツールで、公開サイトのリポジトリを手元に持っているとは限らないため、HTTPで読める場所に置く必要がある。中身は「どの店の日程を Waitinglist の公開APIから取っているか」だけで、**認証情報も非公開情報も含まない**（`displayId` は同APIから誰でも辿れる公開値）。検索結果に出す意味は無いので `robots.txt` で `Disallow: /auto-import-stores.json` にしてある
- **⚠ 運用メモ**: GitHub Actions のスケジュール実行は、**リポジトリが60日間まったく活動しないと自動的に無効化される**（GitHubの仕様）。無効化された場合はActionsの画面から手動で再有効化する。このワークフロー自身が差分をコミットするため通常は活動が途切れないが、日程に変化が無い期間が続くとコミットが発生しない点に注意

      ```sh
      bash -c '
      WF=.github/workflows/monitor-instagram-apify.yml
      cleanup() {
        trap - EXIT INT TERM HUP
        echo ""
        echo "--- 無効化に戻します ---"

        gh workflow list --all | grep -i instagram || true
      }
      on_signal() { cleanup; exit 130; }
      trap cleanup EXIT
      trap on_signal INT TERM HUP
      gh workflow enable "$WF" || exit 1
      gh workflow run "$WF"
      sleep 15
      gh run watch "$(gh run list --workflow="$WF" --event workflow_dispatch --limit 1 --json databaseId --jq ".[0].databaseId")" --exit-status

      - **なぜ `trap` か**: `;` でつなぐ形は「前段が失敗しても disable する」は守るが、
        **Ctrl-C や端末を閉じた場合には `disable` に到達しない**(中断は失敗ではないため)。
        そこを通り抜けると**workflow が有効のまま残り、次の07:10 JSTに無条件・本番・無人の実行が走る**。
        `trap` で EXIT/INT/TERM/HUP を捕まえれば、**正常終了・エラー・Ctrl-C・端末クローズのすべて**で
        無効化に戻る(4経路とも実測済み。いずれも `disable` の呼び出しは1回)
      - **なぜ `bash -c` で包むか**: 対話シェルにそのまま貼ると EXIT トラップは**シェルを閉じるまで**
        発火しない。サブシェルに閉じ込めることで、このコマンドの終わりが trap の発火点になる
      - **★`bash -c` を外さないこと★**: 外して本文だけを対話シェルに貼ると、**正常終了しても
        EXIT トラップが発火せず `disable` が呼ばれないまま workflow が有効で残る**(zsh/bash とも実測)。
        このとき `--- 無効化に戻します ---` の行も状態表示も**出ない**ので、
        **その2行が出なかったら有効のまま残っていると判断し、`gh workflow disable "$WF"` を手で叩くこと**
        (「出るはずのものが出ない」を検知の合図にする)
      - **`trap -` による再入防止は bash 固有の挙動に依存している**: zsh でスクリプトとして同じ本文を
        実行すると、関数内の `trap - EXIT` が EXIT トラップを解除しきらず `disable` が2回走る
        (結果は無効化で安全だが403のノイズが出る)。`bash -c` を別のシェルに変えないこと
      - **`cleanup` 冒頭の `trap -` は必須**: `gh workflow disable` は**冪等ではなく**、すでに無効な状態で
        もう一度叩くと **403** で赤くなる。シグナル経路の後に EXIT トラップが再度走ると二重に叩いてしまう
        ため、`cleanup` の先頭で自分自身を解除している(手順の外で追加の `disable` を叩いた場合も
        同じ理由で403になる。無効という結果は同じ)
      - **最後に必ず状態が表示される**。ここが `disabled_manually` でなければ**有効のまま残っている**ので、
        手で `gh workflow disable "$WF"` を叩くこと

      - **`gh run list` の `--event workflow_dispatch` は外さないこと**。付けないと `sleep 15` 以内に
        新しいrunが現れなかったとき、**直前の `schedule` のrun(過去の失敗)を掴んで**「dry-runが失敗した」と
        誤読する
    - 実行したら**runのログ先頭が「実行モード: DRY-RUN」であることを必ず目視で確認**してから内訳を読む
      (ここが「本番」なら即座に止める。バックログを消費している)

      同じ店・同じ日・同じ開始時刻の別大会は日本語名だと必ず衝突する。層2で捨てないと層1が落ち、
      state が進まないまま毎日同じ所で止まる
    - 層1のゲートは**日付以外に id重複・件数も見る**。層2が写しているのは1行で判定できる規則だけなので、
      「層2を通れば層1も通る」は**自動的には成り立たない**。検査を足すときは両方を確認すること
  - **捨てた行はログに残す**: 「理由 / 店 / 投稿URL・投稿日時 / 実際の `date` と `name`」を1行で出す
    (Visionの抽出品質を人が測れることが要件)。店ごとのサマリにも `破棄した抽出行 N件` が出る
  - **投稿から1行も採用できなかった場合は異常扱い**: その投稿の内容はサイトのどこにも残らず、
    確認済み投稿日時は進むので**二度と再試行されない**。静かに捨てると誰も気づけないため、
    GitHub Actions の `::error::` 注記で目立たせる。ただし**ジョブは落とさない**(落とすと上記の
    「状態が進まない」問題に戻るため)。内容が必要なら
    `node tools/import-venue-image.js --venue <id> --instagram-url <投稿URL>` で手動取込みする。
    全店で同じ理由が続くようなら `tools/venue-schedule-vision.js` のプロンプト/モデルを疑う
    - 注記(`::error::` 等のワークフローコマンド)は**必ず stdout に出す**こと。GitHubの仕様は
      "sent to the runner over stdout" で、stderr で注記として認識される保証が無い
    - **【例外】店の再投稿は異常にしない(2026-07-31追加)**: 同じ画像が再投稿されると2件目の
      投稿は全行が「既に取込み済み」(`duplicateIdProblem` の `kind='duplicate-in-run'`)で捨てられ
      採用0件になるが、**内容は1件目で取り込めており何も失われていない**。店の再投稿はよくあることで、
      これを `::error::` にすると**初回実行という一度きりのrunで唯一の警告チャネルが空振りで埋まり、
      本物の異常が読めなくなる**。そのため「破棄理由がすべて `duplicate-in-run`」の投稿は異常から
      除外し、`再投稿と判断しました(異常ではありません)` の1行と件数(`lastExtraction.reposts`)
      だけ残す。判定は**理由の文面ではなく `kind`** で行う(文言を直した瞬間に静かに壊れるため)
    - 一方 `kind='existing-slot-conflict'`(`data.js` に同じidで**別の日時**の既存がある)と、
      重複と別理由が混在する投稿は、**内容がどこにも入らないままなので従来どおり異常**として扱う
  - **件数は `apify-monitor-state.json` に残す**: 注記は「緑のrunに赤い注記が付く」だけなので
    **通知は飛ばず**、runログも既定90日で消える。それだけでは「Visionの抽出品質を人が測れる」を
    満たせないので、店ごとに
    `lastExtraction: { checkedAt, posts, kept, dropped, normalized, unusablePosts, reposts }` を
    同じ状態ファイルに書く。このファイルは元から毎回コミットされるので**git履歴に差分として残る**
    (`normalized` はVisionの出力形式がどれだけ揺れているかの指標。`reposts` が無いと
    「`dropped` が多いのに `unusablePosts` が0」の理由が読めない)。
    別ファイルにせず相乗りさせたのは、このファイルの**書き手がこのスクリプト1つだけ**で、
    書き込みも1回のJSON書き出しに閉じており、並行編集で消される事故が起こらないため。
    Vision抽出を実際に行った店だけ更新し、行っていない店は前回値を持ち越す(毎回変わる値を足すと
    日程に変化が無い日でも差分が出て、無意味な日次コミットが増えるため)
- **Visionの出力が途中で切れた場合(2026-07-31追加)**: **切り捨ては「切り捨て」として失敗させる。
  パースを通す方向に直してはいけない**
  - 症状: 2026-07-31 の dry-run で6投稿(v20/v18/v21×2/v35×2)が
    ``Unexpected token '`', "```json\n[\n"... is not valid JSON`` で丸ごとスキップされた
  - 真因は**フェンス除去のバグではない**。`max_tokens: 2048` に対して月間スケジュールのJSONが
    大きすぎて出力が途中で打ち切られ、**閉じフェンスが出力されなかった**ため、
    「``` で囲まれた部分」を拾う正規表現が空振りして生テキストをパースしていた
  - **ここで正規表現を「閉じフェンスが無くても拾う」形に緩めてはいけない**。エラーは消えるが、
    **途中で切れたJSONが部分的に通り、月の後半が丸ごと欠けた日程が無言で公開される**。
    実測では124行の月が**22行だけ取り込まれ、102行が静かに消えた**(エラーも警告も出ない)。
    取り込めずエラーになる今の方がまだ安全
  - 対策は2本立て:
    1. **切り捨ての明示的検出** … Anthropic APIの `stop_reason` を本文のパースより**先に**見る。
       `max_tokens` なら「max_tokensで打ち切られた」と分かる文面で失敗させる。
       `end_turn` / `stop_sequence` 以外(`refusal` など、モデルを差し替えたときに増える値)も
       素通しせず失敗させる。加えて `extractJson` は**開きフェンスがあるのに閉じフェンスが無い**
       応答を明示的なエラーにする(フェンスが最初から無い純粋なJSONは従来どおり通す)。
       ストリーミングでは**`stop_reason` を返さないまま終わったストリーム**(接続断)も
       同じ「途中で切れた」として失敗させる — これも部分採用すれば同じ被害になるため
    2. **そもそも切り捨てない** … `MAX_OUTPUT_TOKENS = 32768`
  - **容量の3定数は必ずセットで動かす**。`MAX_EXPECTED_ROWS`(捨てずに通す行数)/
    `WORST_CASE_TOKENS_PER_ROW`(1行あたりの実測トークンの**最悪値**)/ `MAX_OUTPUT_TOKENS`(出力上限)は
    `MAX_EXPECTED_ROWS × WORST_CASE_TOKENS_PER_ROW ≤ MAX_OUTPUT_TOKENS` を満たす必要がある。
    - **最初の実装はここが矛盾していた**: 「200行までは捨てずに通す」と宣言しながら
      `max_tokens` は166行分しか無く、**守るはずの月がその手前で切り捨てられる**状態だった
    - 数字は**実トークナイザでの実測**を置く。文字数からの概算(「ASCII=3文字/トークン」等)は
      実測より2〜3割少なく出て、足りない値を選んでしまう。実測は
      1行あたり**実分布95.2〜98.5トークン / 全項目が埋まった行 約123.3トークン /
      全項目が埋まり大会名が日本語だけの行 約130.4トークン(全シナリオ中の最大)**
      → `WORST_CASE_TOKENS_PER_ROW = 131`(切り上げ)。200行 × 131 = **26,200トークン**に対し
      `MAX_OUTPUT_TOKENS = 32768` は約25%の余裕。`claude-sonnet-4-5` の最大出力64,000の半分
    - **定数名が `WORST_CASE_` である理由**: ここに平均や「レンジの下の方」を置くと、整合assertが
      **「通ったのに実際には危ない」を許す**。例えば123.3(日本語名を含まない値)を置いたまま
      `MAX_EXPECTED_ROWS` を250に上げると `250×124=31,000` で通るが、実際の最悪値では
      `250×130.4=32,600` で余裕がほぼ消える。**常に「観測された最大」を置くこと**
    - 整合は `tools/venue-schedule-vision.test.js` が**直接assert**している(定数を下げると落ちる)
    - **旧値2048の裏付け**: 131トークン/行なら2048で出せるのは15〜16行(実分布の98.5でも20〜21行)。
      dry-runで「1投稿20件前後」の投稿は通り、月まるごとの日程表だけが落ちた観測と一致する
  - **`max_tokens` が ~16K を超えるならストリーミング必須**。Anthropicの移行ガイドは
    「非ストリーミングは高い `max_tokens` でHTTPタイムアウトに当たる。~16Kを超えるなら全モデルで
    ストリーミングすること」と明示している。`MAX_OUTPUT_TOKENS = 32768` に伴い
    `callVisionModel` は `stream: true` のSSEに移行済み。**非ストリーミングに戻さないこと**
    (テストで `stream: true` を固定してある)。切り捨てのエラー文にもこの注意を入れてあるので、
    運用者が「タイムアウトを伸ばす」誤った方向に進まない
  - **タイムアウトは「全体」ではなく「無音」で測る**(`STREAM_IDLE_TIMEOUT_MS = 120000`)。
    旧実装の「全体60秒」が成立していたのは上限が2048で生成が約30秒で頭打ちだったからにすぎず、
    上限だけ上げると「切り捨て」が「AbortErrorでスキップ」に変わるだけで何も直らない。
    生成中のSSEは1秒未満の間隔でイベントが流れるので、無音で測れば
    **「接続が死んだら2分で赤くなる」と「本当に長い月は最後まで待てる」を両立**できる
  - **ジョブ全体の上限はワークフローが持つ**。`.github/workflows/monitor-instagram-apify.yml` に
    `timeout-minutes: 60` を明示してある(既定の360分では、何かが固まったとき6時間気づけない)。
    Vision 1回あたりの無音上限だけを見て全体の所要時間を推し量らないこと —
    Apify取得・画像DL・`git pull --rebase`・`gen-venue-pages`・`gen-sitemap` が同じジョブに乗る。
    実測は初回バックログ(Vision 27回)で約10分、`max_tokens` を上げた後の見積りで20〜40分
  - 1枚の画像から `MAX_EXPECTED_ROWS = 200` 行を超えて返った場合は警告を出す(捨てはしない)。
    月は最長31日・1日6開催でも186行なので、超えるのは月間スケジュール以外の画像を読んでいるか
    同じ行を繰り返している可能性が高い。**本当に大きい月を落とす方が実害が大きい**ので例外は投げない
  - **配列でない応答を黙って0件に潰さない**。以前は `Array.isArray(result) ? result : []` で、
    Visionが `{"tournaments": [...]}` のように包んで返すと**警告も破棄件数も出ないまま0件**になり、
    店ごとのサマリは「1行も採用できなかった投稿 0件」と表示していた(=積極的な誤報)。
    中身は失われているのだから、失われたと言えなければならないので明示的に失敗させる
- **投稿と行の「保存則」(2026-08-01追加)**: **静かに失われる経路を、個別に塞ぐのではなく
  構造的に塞ぐ**
  - **何が起きていたか**: 2026-07-31 の dry-run で、72投稿すべてがVision抽出に失敗しながら
    `::error::` も `::warning::` も1件も出ず、店ごとのサマリは
    **「1行も採用できなかった投稿 0件」= 異常なし** と表示していた。
    集計から漏れていたのではなく、**サマリが積極的に誤報していた**
  - **原因**: 1投稿がたどる結末は6通りあるのに、**3つがどのカウンタにも入っていなかった**
    (画像DL失敗 / Vision抽出失敗 / Visionが0件)。とくに0件は `console.warn` すら出なかった
  - **なぜカウンタを足すだけで終わらせないか**: それでは**7本目の結末が生まれたときに同じことが
    起きる**。実際この不具合は「経路が3本漏れていた」のではなく「漏れても誰も気づけない構造」だった
  - **対策 = 3つの保存則をコードとテストで固定する**
    1. **取込みレベル**(`checkIntakeAccounting`):
       `Apifyが返した件数 = 形式不正 + 投稿日時が読めない + 既読 + 画像を見ずに対象外 + 判定対象`
       — 保存則の左辺を**取込みの最上流まで遡らせる**。`normalizeApifyItem` の欠落判定と
       `pickNewPosts` の日時判定で捨てられた投稿は、下流のどのカウンタにも現れないのに
       `lastPostedAt` だけは前進する(=二度と処理されない)ため、いちばん見えにくい
       (`fetchInstagramPosts(handle, { stats })` が生件数と除外件数を書き戻す)。
       **⚠「画像を見ずに対象外」(`filteredOutCount`)は 2026-08-04 以降つねに0** —
       キーワード判定を廃止し、新着は全件 Vision に渡すため。
       枠を残してあるのは、**将来また前段の絞り込みが増えたときにそこで表に出すため**
    2. **投稿レベル**(`checkPostAccounting`)。**バケツは12個**:
       `判定対象の投稿 = 取り込めた + カレンダーでない + 過去月のカレンダー + 未確認(採用後に打ち切り)
       + 判定済み(キャッシュ) + 再投稿 + 大会なし + 人の訂正と衝突 + 全行不採用
       + Vision抽出失敗 + 画像DL失敗 + Vision0件`
       **将来ここに `continue` を1本足すとテストが即座に落ちる**。
       **★バケツを1つ増やしたら `makeStoreSummary` の初期値も必ず足すこと** —
       足し忘れると合計が `NaN` になり、`NaN === 判定対象数` は常に偽なので
       **全店・毎回「投稿の集計が合わない」と誤報する**(2026-08-04 に実際に踏んだ。
       `tools/monitor-instagram-apify.test.js` の
       「★保存則: 実装が作った summary をそのまま checker に通す」が名指しで検出する)
    3. **行レベル**(`checkRowAccounting`):
       `Visionが返した行 = 追加 + 更新 + 変更なし + 過去日 + 破棄 + 不採用の投稿の行`。
       **★最後の項を忘れないこと** — 新方式では**大半の投稿が不採用**で、その行も
       Vision は返している。数えないと**正常な実行で毎回「行の集計が合わない」と誤報する**
       (これも 2026-08-04 に実際に踏んだ)。不採用と判断した**その場で** `rows.length` を足す
       (残差で出すと保存則が恒等式になる)。
       **過去日は `mergeStore` の中で静かに落ちていた**ので `stats.pastDated` を新設した。
       これが無いと「久留米: 抽出20 / 破棄0 / 追加0」のような、行の行き先を誰も説明できない
       数字が並ぶ(正常に全部過去日だったのか、別の経路で消えたのか区別できない)
  - **合わなければ `::error::`** を出す(残余の件数付き)。合わないこと自体がバグの証拠
  - **⚠⚠ 保存則の項を「残差」で定義しないこと(この落とし穴に2回はまっている)**
    - **1回目**: `stats.pastDated` を `scraped.length - rawFuture.length`(= rawFuture に
      入らなかった全て)で定義していた。`rawFuture` の絞り込み条件を1つ足すだけで
      **未来日の行が黙って消えても差分が `pastDated` に吸い込まれ「過去日 1」と積極的に誤報**された
    - **2回目**: 取込みレベルを足したとき、`malformed` / `invalidPostedAt` / `alreadySeen` /
      `filteredOut` の**4項すべてを隣接する段の差**で数えてしまった。これは
      **望遠鏡和**(`(a−b)+(b−c)+(c−d)+(d−e)+e ≡ a`)で、合計は**絶対に元の件数と一致する** —
      つまり検査として完全に無意味だった。実際、正規化の後に絞り込みを1段足すと
      **未読の投稿が消えたのに「既読」と誤報**された
    - **必ず「その性質を持つこと」そのものを正の述語で数える**。
      `scraped.filter((t) => t.date < today).length` /
      `items.filter((it) => normalizeApifyItem(it) === null).length` /
      `sorted.filter((p) => Date.parse(p.postedAt) <= lastMs).length` /
      「不採用と判断したその場で `rows.length` を足す」(`notAdoptedRows`)のように書く
    - **見分け方1(項の作り方)**: 保存則の各項が `A.length - B.length` の形をしていたら、
      その保存則は恒等式である可能性が高い。「その段で**何が起きたか**」ではなく
      「**通り抜けなかった全部**」を数えているため、新しい消失経路が必ず既存の項に吸収される
    - **見分け方2(比べる相手)**: **左辺が、右辺と同じ材料から導出した値になっていないか**。
      例えば店レベルの保存則を最初
      `observed = summaries.length - failed` として **`summaries.length` と比べた**ため、
      式が `(N - failed) + failed === N` となり**常に成立**していた(3本目の再発)。
      **比べる相手は必ず「外側にある独立した数」**にすること
      (この例では `summaries` ではなく**対象店舗の数**)。
      そうして初めて「記録し忘れた店」が残余として出る
    - **保存則を1本足すたびに、この2点を確認すること。** 実際この案件では
      **同じ罠に3回はまった**(`pastDated` の残差 → 取込みの望遠鏡和 → 店レベルの自己比較)
    - 副次的な利点として、`filteredOut` を同じ述語で数えるとキャプションを出力するループと
      件数が構造的に一致する(残差だと「件数だけ増えてログには出ない」が起こりうる)
    - 回帰テストは**各段に絞り込みを1つ注入して CLI を回し、残余が出ること**を確かめている
      (`R-1:` で始まるテスト)。この形でしか「恒等式ではない」は確かめられない
  - **検知側にもテストを置くこと**。「健全な入力で `ok` が true になる」テストだけでは、
    `ok: actual === expected` を `ok: true` に潰す変異も、`if (!row.ok)` を `if (false)` にする変異も
    生き残る。**壊れた入力で偽になること**と、**その結果 `::error::` が実際に stdout に出ること**
    (CLIレベル)まで固定してある
  - **重大度の使い分け**: 画像DL失敗・Vision抽出失敗・全行不採用は内容が確実に失われるので
    **赤(`::error::`)**。Visionが0件は**黄(`::warning::`)**。0件を赤にすると、
    `duplicate-in-run` を異常から外したのと同じ理由(唯一の警告チャネルが空振りで埋まり
    本物の異常が読めなくなる)に抵触する
    - **ただし「0件だから安心」と読める表示にしないこと**。0件は
      (a)日程を含まない投稿を拾った(=何も失われていない) と
      (b)日程表なのに読めなかった(=内容が失われ再試行もされない) の**どちらでも同じ数字**になる。
      **機械が分類できない以上、機械に分類させない**(人のゲートに置く)。
      そのぶん表示側では、件数が0でない限り
      `(要確認: 日程を含まない投稿か、読めなかったか判別できません)` を必ず添える(`emptyCaveat`)。
      **サマリが安心させる方向に誤解を招くのは、この案件で繰り返し出た失敗の形**
      (72投稿すべてが消失しながら「1行も採用できなかった投稿 0件」と表示していたのと同じ)
  - **件数は `lastExtraction` に残す**(git履歴に残る)。runログは既定90日で消えるため。
    追加したのは `apifyRaw` / `malformed` / `invalidPostedAt` / `alreadySeen` / `newPosts` /
    `filteredOut` / `importedPosts` / `visionFailed` / `imageFailed` / `emptyResult` /
    `notATournamentPosts` / `humanEditedPosts` /
    **`notCalendar` / `pastCalendar` / `unexamined` / `cacheHit`**(走査フェーズの行き先) /
    `visionRows` / **`notAdoptedRows`** / `pastDated` / `added` / `updated` / `unchanged`。
    **走査フェーズの4つが無いと**、状態ファイルには「新着12件・取込み0件」しか残らず、
    「カレンダーを1枚も出していない店」なのか「カレンダーはあるが過去月ばかり」なのかが
    **git履歴から読めない**(runログは90日で消える)
  - **記録する条件は「取り込めた店」ではなく「新着に何かあった店」**(実装は
    `if (summary.newPostCount > 0)`)。取込みの有無を条件にしていると、
    **折尾のような「新着12件→取込み0件」の店で `lastExtraction` 自体が書かれない** —

    「runログは90日で消えるから永続化する」という理屈が破れる

### 実行モードと引数（`--dry-run` / `--probe` / 知らない引数）

| 呼び方 | 何をするか | 書き込み | `lastPostedAt` |
|---|---|---|---|
| `node tools/monitor-instagram-apify.js` | 本番。最新の当月カレンダー1枚を採用して取り込む | する | **前進する（不可逆）** |
| `… --dry-run` | 本番と**同じ判断**をして、書かない予行 | しない | 前進しない |
| `… --probe` | **探索専用**。打ち切らずに全投稿を判定して数えるだけ（採用しない） | しない | 前進しない |
| `… --dryrun` など知らない引数 | **何もせず `exit 1`** | しない | 前進しない |

**知らない引数を黙って無視しない。** 以前は `--dry-run` の打ち間違い（`--dryrun` / `--dry_run`）が
**そのまま本番実行**になった。この経路の本番は不可逆（拾えなかった投稿は自動経路から永久に失われる）なので、
**打ち間違いを本番にしない**ことを構造として持たせてある。
テスト『★CLI: 知らない引数は本番実行にならず、何も書かずに止まる（打ち間違い対策）』が、
**弾く側（4通り）と通す側（`--dry-run` / `--probe` / 引数なし）の両方**を固定している
（片側だけだと「全部弾く実装」でも緑になる）。

**⚠ ワークフローが渡す引数を増やすときは、`KNOWN_FLAGS` にも足すこと。** 足し忘れると
その日から `exit 1` で毎朝止まる（`.github/workflows/monitor-instagram-apify.yml` が渡すのは
現在 `--dry-run` だけ）。

### 確認済み投稿日時の記録が壊れたときの縮退（リスク台帳 #19 の解消・2026-08-05）

**変更点**: `apify-monitor-state.json` を JSON として読めないとき、**落とさずに「記録なし」として続行する**。
以前は `throw` → `fail()` → `exit(1)` で、**書き込みが起きないので翌朝も同じ理由で落ちる**（人が直すまで毎朝止まる）。

#### ⚠ まず発生経路を正確にしておく（監査 #37 の書き方への補足）

全数監査（#37）は起票理由に「**bot 自身が毎日書いてコミットするので `git pull --rebase` の衝突や部分書き込みで壊れうる。机上の話ではない**」と書いている。
**このうち「Actions の実行が壊れたファイルを `main` に残す」経路は、いまのワークフローでは成立しない**（コードとワークフローを読んだ結論であって、実験したわけではない）：

- ジョブは毎回 `actions/checkout` から始まるので、**前回の作業ツリーは残らない**
- `git pull --rebase` が衝突すると、その時点でステップが失敗する（GitHub の `run:` は `bash -e`）。
  衝突マーカーの入ったファイルは**コミットも push もされない**
- 書き込み途中でジョブが落ちた場合も同じで、後続のコミットステップに到達しない
- そもそも `apify-monitor-state.json` を書くのはこのワークフローだけで、`concurrency` で同時実行も止めてある

**それでも落とさない側に倒す価値はある。** 実際に壊れた状態が `main` に載りうる経路は残っている：
**人が PR の衝突を解決し損ねてコミットする / 手で編集する / 手元で実行して壊れたファイルをコミットする / 将来ワークフローが変わる**。
いずれも「稀だが起きたら毎朝止まる」性質で、**止まったときに人が気づいて直すまでの日数**がそのまま損失になる。

#### なぜ「落とさない」側に倒したのか — **もう一方の状態ファイルに揃えたのではない**

判断の材料は**その状態が空になったときにどちらへ倒れるか**の1点だけ。

| ファイル | 何を持っているか | **空にすると何が起きるか** | 落とす／落とさない |
|---|---|---|---|
| `apify-monitor-state.json` | `lastPostedAt`（どこまで見たか） | **取得窓の投稿を全部もう一度読み直す。取りこぼしは構造的に起きない**（取りこぼすのは記録が「進みすぎた」ときで、空はその逆側） | **落とさない** |
| `instagram-write-state.json` | 機械が最後に書いた値の控え | **全行が「人のもの」扱いになり、機械は新しい枠に足すだけになる**（人の行が守られる側） | **落とさない**（従来どおり） |

**両方とも「落とさない」だが、理由は別物である。** 前者は*やり直しになるだけ*だから、後者は*人の行が守られる*から。
**「同じツールなのだから揃える」という理由では決めていない。**

**★次に状態ファイルを足す担当へ**: この理由は**空にしたときに取りこぼす種類の状態には効かない**。
たとえば「処理済みIDの集合」を持つファイルなら、空にすると**再送・二重投稿**になりうる。
そのときは落とす／落とさないを**その性質からもう一度決めること**（ここを引き写さない）。

#### 続行にも代償がある — だから黙って続けない

- **費用と時間**: その店の取得窓（実測で1店あたり直近12投稿）を Vision に渡し直す
- **履歴の消失**: `checkedPosts` / `lastExtraction` が失われる（**git履歴には残る**ので `git log -p -- apify-monitor-state.json` で読める）
- **★人が消した行が復活しうる（リスク台帳 #15）**: 同じカレンダーを読み直すため。
  現行の規則では「行を消す＝その枠を機械に引き渡す」なので**復活自体は規則どおり**だが、
  平常は「既読なので読み直さない」ことで**結果的に起きていない**。記録を失うと**その偶然の保護が外れる**

そのため**必ず `::error::` 注記で人に見せる**。ただし**終了コードは変えない**。

#### ★この判断は #15 に依存している（#15 を動かす人は必ずここを読むこと）

**「落とさずに続行する」を選べたのは、続行の代償の1つ（人が消した行が復活する＝#15）が
「明示的に受容」された状態だからである。** #15 の受容が変われば、この判断の前提も変わる。

- **#15 に対処が入るとき**（例: 墓標＝「人が消した」ことを機械が覚える仕組み）は、
  **#19 の「続行する」も再評価すること**。復活が起きなくなるなら代償が1つ減るので判断は強くなるが、
  逆に「消した行を機械が二度と書かない」規則を入れると、**取得窓を読み直すこと自体の意味が変わる**
- **#22 の「自動で戻さない」も同じ依存**（下記）。`lastPostedAt` を機械が巻き戻すと窓を読み直すので、
  やはり #15 が発動する。**#19 / #22 / #15 は同じ結び目の上にある**

**★ここでジョブを赤くしてはいけない（この判断がいちばん効いている）**:
非ゼロ終了すると後続のコミット・pushが走らず、**直った状態ファイルがリポジトリに残らない**。
壊れたファイルが `main` にある場合、翌朝も同じものを読むので**「落として止める」のと同じ永久ループに戻る**。
自己修復は**最後まで走り切ること**に依存している。

#### 新着0件の日でも書き直す

全店で新着0件の日は次の状態が（空の）現在の状態と一致するので、**差分だけを見て保存を決めると壊れたファイルが残る**。
`loaded.broken` のときは差分の有無に関わらず書き直す。

### 静かな永久停止（リスク台帳 #22）— 矛盾の検知と、原因を問わない測定

**症状**: `lastPostedAt` が**未来**になっていると、`pickNewPostsWithStats` が取得した全投稿を
「既読」と判定する。ログ上は**「新着0件」＝ 店が何も投稿していない平常日と区別が付かない**まま、
その店の取込みが**永久に止まる**。`#19`（壊れて毎朝赤くなる）より**見えない**ぶん質が悪く、
**cron 後は誰も気づく手段がない**ので cron 前提条件に格上げされた（2026-08-05）。

#### ★「両方向を実データで示す」規律は、ここには適用されない — 矛盾は仮説ではない

**この区別は記録に値するので残す。** この案件が一貫して禁じてきたのは
**閾値や経験則にもとづく警報で、両方向を実データで示せないもの**である
（PR #32 の到達不能な上振れ分岐 `pct > 120` が典型）。

**一方、`lastPostedAt` が未来であることは経験則ではなく【矛盾】である。**
投稿日時が現在より未来という状態は物理的に存在しない。
**ありえない状態の検出は仮説の検証ではないので、「鳴る側」を実データで示す必要がない**
（定義上、正常なデータの中にその状態は存在しない）。

| 種類 | 例 | 両方向の実データが要るか |
|---|---|---|
| **閾値・経験則にもとづく警報** | 「開始時刻が読めない行が◯%を超えたら」 | **要る**（要求できないなら入れない） |
| **矛盾の検出** | 「投稿日時が未来」「件数の合計が合わない」「同じidが2行ある」 | **要らない**（正常なデータに存在しない状態なので、鳴る側の実データは原理的に取れない） |
| **測定（警報ではない）** | `EXPECTED_NO_START_PCT` の割合、下記の「取込みが成立してからの日数」 | **要らない**（判断するのは人。閾値を置かない） |

**★線引きを間違えると両方向に失敗する。** 矛盾の検出に実データを要求すると**必要な検査が入らず**、
経験則の警報で実データを免除すると**常時点灯する警報が増える**。**どちらなのかを先に決めること。**

#### 実装（レビュー部の指定に従った条件）

- **`fail()` にしない**。`#19` の教訓がそのまま当てはまる — 非ゼロ終了すると後続のコミット・pushが
  走らず、他店の取込みも状態の前進もリポジトリに残らない。**`::error::` 注記だけで人に見せる**
- **自動では戻さない**。`lastPostedAt` を機械が消す／巻き戻すと取得窓を読み直すので、
  **人が消した行が復活する（#15）**。どちらが軽いかは中身を見ないと決められないため、
  機械は判断せず、**直し方とその副作用をログに書いて人に渡す**（上の「#15 に依存している」参照）
- **比較の相手は「実行日（JST）の終わり + 1日」**。秒単位の時計ずれで誤検知しないための余裕であって、
  **調整するための閾値ではない**（1日先の投稿がありえない点は変わらない）

#### あわせて入れた「原因を問わない測定」— 取込みが成立してからの日数

**店ごとに「最後に取込みが成立した日から何日経ったか」を毎回必ず出す**（`lastImportedAt` を状態ファイルに控える）。

- **これは警報ではなく測定**。店が月に1度しかカレンダーを出さない以上、30日近い値は**平常**であり、
  閾値を置けば毎月点灯して意味を失う（`EXPECTED_NO_START_PCT` と同じ扱い）
- **成立の定義は「data.js の行が増えた／変わった」**。`unchanged`（同じカレンダーを読み直しただけ）は
  **含めない** — 含めると、その投稿が取得窓に残っている限り毎日「成立」になり、**止まっていることが見えなくなる**

#### ★なぜ両方入れたか（片方では埋まらない）

| | 検知（#22・矛盾） | 測定（日数） |
|---|---|---|
| 気づく速さ | **即日** | 何日か経ってから |
| 対象 | **未来日という1つの原因だけ** | **原因を問わない**（Apifyが常に空を返す／カレンダーが一度も一致しない／店が投稿をやめた…） |
| 出力 | 異常時だけ `::error::` | **毎回必ず1行** |

**検知は「早いが狭い」、測定は「広いが遅い」。** 片方だけにすると、それぞれ
「未来日以外の停止が見えない」「気づくのが数週間遅れる」という穴が残る。
どちらも安いので両方入れた。

### #13 の測定：探索専用モード（`--probe`）

**目的**: 「本番の走査が打ち切る位置より後ろに何があるのか」を、**採用も書き込みもせずに**数える。
現在の走査は当月カレンダーを見つけた時点で打ち切るため、
run `30922261347` では **71投稿中28投稿しか判定されず、43投稿は誰も中身を見ていない**。
その43件こそ #13 が問題にしている集合そのもの。

#### 何を数えるか

各店について、**走査の並び（新しい順）における位置**で分けて数える。

| 数字 | 意味 | 読み方 |
|---|---|---|
| **採用より【新しい位置】にあり、カレンダー判定を満たす投稿** | 形だけなら本物を追い越せた投稿 | **ここに入りうるのは過去月のカレンダーだけ**（当月以降なら採用側になるため）。**月の判定だけが偽陽性を止めている**件数 |
| **採用より【古い位置】にある当月以降のカレンダー** | 打ち切りの後ろに隠れた候補 | **本番の走査は到達しないので、探索でしか観測できない**。0でなければ、採用した1枚が本物かを人が画像で確かめる |
| 形が確定していない投稿（画像DL失敗 / Vision抽出失敗 / Vision 0件） | 判定できなかった投稿 | **この数が0でない限り、上の2つは「見えた範囲での件数」**。必ず併記する |
| **★採用が窓内で最もカレンダーらしい投稿か（形状比較）** | **#13 の署名そのもの** | **分類を経由しない**ので、上の2つが構造的に見落とす形（下記）でも効く。**店ごとに1行**出す |

**★レビュー部が指定した数字（「採用されたカレンダーより新しい位置にある投稿のうち、カレンダー判定を満たすもの」）は、
それ単独では #13 の主要な形を検出できない。**
採用位置は「新しい順で最初の当月以降のカレンダー」なので、**それより新しい位置に当月以降のカレンダーは定義上存在しない**。
レビュー部自身の再現（8月カレンダーの後にシリーズ告知が投稿され、シリーズ告知が採用される）では
**この数字は0**になる一方、本物は後ろで潰れている。
**だから「古い位置」側も必ず数える。** 実装・ログ・テストのすべてでこの2つを並べて出している
（テスト『★探索(#13の再現): 本物のカレンダーが打ち切りの後ろに隠れていることを数える』が、
まさに「0件 / 1件」になることを固定している）。

#### ★形状比較 — #13 の署名は「採用が、その店の窓内で最もカレンダーらしい投稿ではない」こと

**上の2つの数字は【分類】に依存している**（カレンダーか否か・当月か過去月か）。したがって
**採用が偽陽性 かつ 後ろの本物も偽陰性**だと、本物がどちらの数にも入らず
**0のまま実害が起きる**。両方の誤りが同時に必要なので確率は低いが、
**cron の可否を決める証拠としては潰しておく**（2026-08-05・レビュー部の指定）。

そこで**分類を経由しない指標**を足した。店ごとに1行、次を並べる：

```
形状比較: 店=… / 採用=異なる日付5・広がり27日
                / 窓内の最大=異なる日付20・広がり29日(採用より【古い位置】/ 判定=calendar-past / <URL>)
                / ★採用は窓内で最もカレンダーらしい投稿ではない(#13 の署名)
```

- **比較の母集団は「形が確定した全投稿」**。カレンダーと判定されたものに限らない —
  限ると、まさに拾いたい偽陰性（本物なのに `not-calendar` / 支配月を読み違えて `past`）が母集団から抜ける
- **印が付くのは厳密に小さいときだけ**。同点（同じカレンダーの再投稿など）では付けない
  （付けるとその店で毎回点灯する）
- **合計行にも「★採用が窓内で最もカレンダーらしくない店 N店」**を出す。
  生ログを人が突き合わせる形にすると、**cron 後には誰もやらない**
- **★この指標も万能ではない**: 本物のカレンダーから Vision が**少ししか日付を読めなかった**場合は、
  その投稿の `異なる日付` 自体が小さいので浮かばない。**下の「形が確定していない投稿」と併せて読むこと**

#### ★★実走の結果を読む順序（実走の判断はこの順で行うこと）★★

**合計行に出る4つの数字は、意味も強さも違う。並んでいる順ではなく、次の順で読む。**

```
探索の合計: 本物を追い越せる位置のカレンダー N件 / 打ち切りの後ろに隠れた当月以降のカレンダー N件 /
            追い越せる位置で形が確定しなかった投稿 N件 / ★採用が窓内で最もカレンダーらしくない店 N店
```

| 読む順 | 数字 | 何を意味するか / 何を意味しないか |
|---:|---|---|
| **1番目** | **④ 形状比較（#13 の署名）** | **これだけが分類を経由しない。**0でなければ **#13 の実害が起きている**（採用が偽陽性で、より完全なカレンダーを追い越している）。**①②が0でも④が鳴っていれば実害はある** |
| **2番目** | **③ 形が確定していない投稿** | **0でない限り、①②④のすべてが「見えた範囲での件数」**になる。ここが大きい実行は、他の数字の0を根拠にしてはいけない |
| **3番目** | **② 採用より古い位置の当月以降カレンダー** | **分類に依存する。**0は「後ろに本物が居ない」ではなく「後ろに *当月以降と分類された* カレンダーが居ない」。本物が偽陰性（`not-calendar` / 支配月を誤読して `past`）なら0のまま |
| **4番目** | **① 採用より新しい位置のカレンダー** | **構造的に常に0**（採用位置は「新しい順で最初の当月以降のカレンダー」なので、それより新しい位置に当月以降は定義上存在しない）。**0であることは #13 の否定にならない** |

**要点**: **①②が0でも④が鳴っていれば #13 の実害が起きている。** ①の0を「安全」と読むのは、
レビュー部の指定に見つけた誤りとまったく同じ構図である（「構造的に0になる数字」を根拠にすると、
cron の可否を誤った根拠で決めることになる）。**同じ誤読が実走の読み方でも起こりうるので、ここに残す。**

**④が鳴ったときにやること**: **その店の1行要約（`形状比較:` の行）だけを見ればよい。**
その1行に**2つの投稿URL（採用したもの / 窓内の最大）が両方載っている**ので、両方を開いて
**どちらが本物の月間カレンダーかを人が確かめる**。機械には正解が無い。
（**2つとも同じ行に出ることはテストで固定してある** — 片方を消す変異・取り違える変異のいずれでも落ちる。
異常時に別の行を探させると、1行に集約した意味が無くなるため）

#### ★★④が鳴らなくても「安全」ではない — ゼロを安全と読む最後の形★★

**上の4段は「鳴ったものをどう解釈するか」の話で、この項は「全部鳴らなかったとき」の話である。**

**④が拾えないのは「本物のカレンダーから Vision が【少ししか日付を読めなかった】」場合**である。
そのとき本物の `異なる日付` 自体が小さく出るので、採用との比較でも浮かばない。
**しかもこの場合、③（形が確定していない投稿）にも入らない** — Vision は応答を返しており、
「形は確定した、ただし小さい」という扱いになるからである。**つまり数字が全部0になりうる。**

**したがって、④の「窓内の最大」の絶対値そのものを見ること。**
**実データの月間カレンダーに対して明らかに小さければ、Vision が読めていない可能性がある。**

**比較の基準に使う値（同じ量で測ったもの）**: 探索の判定ログに出る `異なる日付` は、
run `30922261347` でカレンダー判定を満たした15投稿が **6〜29**（本README上表「較正はこのログの実測で行う」）。
**窓内の最大が一桁で並ぶ実行は、月間カレンダーを読めていない疑いがある。**

**⚠ `data.js` 側の件数を基準にしないこと（量が違う）。** 参考までに `data.js`（634件・2026-08-05）で
監視6店の「月ごとの異なる日付数」を数えると次のとおり：

```
$ node -e '…monitor.STORES ごとに data.js の date を月で束ねて Set のサイズを出す…'
v40 2026-08:16 / v20 2026-07:10, 2026-08:14 / v18 2026-07:25, 2026-08:26
v21 2026-07:31, 2026-08:31 / v34 2026-07:4 / v35 2026-07:29
```

**これは「Vision が読んだ日付数」ではなく「data.js に載った行の日付数」で、別の量である。**
取込みの過程で定休日・見出し・リングゲームの行が捨てられるぶん**小さく出る**
（`v34` は dry-run #5 で**19行すべてリングゲームとして捨てられた**例が本READMEに記録されている）。
**判定ログの値と直接比べないこと。**

#### 探索が絶対にやらないこと

- **`data.js` を書かない**。`--probe` は `--dry-run` を含むうえ、**書き込み関数そのものを取り上げてある**
  （`forbidWrite`）。「return が書き込みより前にある」という**並びだけに依存しない**ため
- **採用（マージ）しない**。当月以降のカレンダーを見つけても記録するだけで、`data.js` の配列に触らない
- **状態を1バイトも動かさない**。`runMonitor` が返す状態は**渡された状態とビット単位で同じ**（テストで固定）。
  `lastPostedAt` も `checkedPosts` も `lastExtraction` も動かないので、**バックログを消費しない**
- **判定キャッシュを使わない**。キャッシュは判定の結果しか持っておらず、**支配月・異なる日付・広がりの3値を持っていない**。
  使うと測定に穴が空く。そのぶん Vision の呼び出しは取得窓の全件になる（**費用は探索を回す人が引き受ける**）
- **既読を理由に投稿を落とさない**。既読の投稿も判定し直す。「本番なら既読として飛ばしていた件数」は別項で数える

#### 「探索のつもりが本番だった」を構造で塞ぐ

- `--dry-run` に相乗りさせず**別のフラグ**にした。`--dry-run` は「本番と**同じ判断**をして書かない予行」、
  `--probe` は「**本番とは違う判断（打ち切らない）**をする測定」。同じフラグにすると
  **「予行が通ったから本番も同じはず」という dry-run の意味そのものが壊れる**
- 逆向きの事故（探索のつもりで本番）は、上の**「知らない引数を受け付けない」**が塞ぐ
- 実行の**先頭の1行**に `PROBE(探索専用: …)` と出る（本番で走ってしまったことを目視で拾えるように）
- ワークフローは `--probe` を渡さない。**探索は人が手元で回すもの**

#### まだ測っていない

**このPRで用意したのは測る道具だけで、実測はまだ行っていない。**
実行には `APIFY_API_TOKEN` と `ANTHROPIC_API_KEY`、および取得窓の全投稿ぶんの Vision 呼び出し費用が要る。
**したがって #13 は閉じていない。** 動作確認はスタブ（構成した想定入力）で行っており、
**実データの分布については本節は何も主張していない**（README「`実測` の語法」参照）。

### 人が入力した値を機械が壊さない仕組み（`tools/machine-write-state.js`）

**3つの書き込み経路（Waitinglist取込み / Instagram監視 / 店舗画像の取込み）すべてに効く共通の規則。**

#### 何を直したのか

2026-08-04以前は「同じ (date, start) に取得結果が来たら手入力を置き換える」という規則だった。これには2つの問題があった。

1. **置き換えは値の交換ではなく、多くの場合【情報量の低下】だった。** Instagram監視の dry-run #5 では人の手入力**39件**が Vision の読み取りに置き換わる判定になっていた。実測すると、`v21`（KENポーカー久留米）の未来日28件は**開始時刻23件（82%）・参加費22件（79%）**を持つのに対し、同じ実行の Vision は**開始時刻4.5% / 参加費13.6%**。「人が直したかどうか」以前に、この置き換えには技術的な正当性が無い
2. **⚠ 要確認 が黙って外れていた。** 監視6店の未来日手入力82件は**全件 `lowConfidence: true`**（サイト表示は `⚠ 要確認`）。取込み側の `toTournament` はこの印を引き継がないので、置き換えると**誰も確認していないのに ⚠ が消える**＝「確認済み」という未検証の主張になる
3. **`source: 'auto'` の行は毎朝作り直されるので、人が直した内容が翌朝の実行で機械の値に戻っていた**（Waitinglist側）

#### 仕組み（印を1つも増やさない）

`data.js` の1行を見ただけでは、機械が書いたままなのか人が直したのかは分からない。そこで**機械が書いた値そのものを控えておき、いまの `data.js` と1項目ずつ突き合わせる**。

```
控えと一致    → 誰も触っていない → 機械が更新してよい
控えと食い違う → 人が直した      → その項目は触らない
控えが無い    → 人の行           → その行は一切触らない
```

**社長が「印を付ける」ことを覚える必要は無い。** `admin.html`（＋ `dev-server.py`）は `data.js` を丸ごと吐き直すが、控えのJSONには触らないので、編集は自動的に「控えとの食い違い」になる。**管理コンソール側の変更は1行も要らない**（`fukuoka-poker-admin` はそもそもトーナメントを編集しない読み取り専用の進捗表）。

#### 粒度が2つある理由

| 状況 | 粒度 | なぜ |
|---|---|---|
| **同じidの既存**が人の手で変わっている | **項目単位**（食い違う項目だけ残す） | 行ごと凍結すると、大会名を1つ直しただけで**その行の開始時刻が二度と更新されなくなる**。この案件で最も重い実害は一貫して「プレイヤーが違う時間に店へ行く」ことなので、その設計は採れない |
| **別idの人の行**が同じ (date, start) を占めている | **行単位**（機械の行を書かない） | idが違う行同士は**項目を対応づける根拠が無い**（「この人の行のこの項目」と「この機械の行のこの項目」を結べない） |

社長の優先順位（**トナメ名 > 参加費・開始時間 > 賞金**）は、**保護する項目の取捨には使っていない**。全項目を等しく守るほうが安全で、しかも安く済むため。効かせているのは**報告の並び順**だけ（守った項目を並べるとき `name` / `buyin` / `start` を先頭に出す）。

#### 控えるのは「人の値を戻す前」の機械の値（★ここを取り違えると保護が1日しか持たない）

人の値を戻したあとの行を控えると、翌日は「控え == いまの値」になって食い違いが消え、**人の修正が翌々日に上書きされる**。控えるのは常に「誰も触っていなければ機械が書いたはずの値」＝ `carryOver` 直後の候補行。テストで固定してある（`import-waitinglist.test.js` の 6-4 / 6-5 は**2日ぶんを実際に回して**確かめる）。

#### seed（状態ファイル導入前に機械が書いた行の引き継ぎ）

導入時点で `data.js` にある機械の行には控えが無い。これを素直に「人のもの」とすると**稼働中の取込みが数週間凍結**し、しかもログに毎朝「守った49件」と常時点灯する（この案件が一貫して排除してきた形）。そこで**例外を1つだけ、狭く**置いている。

```
控えが無くても、id が【その取込みツール自身の名前空間】で始まり、
かつ source === 'auto' なら、機械のものとして扱い控えを取り直す。
```

- **根拠**: `wl-<ULID>` の ULID は API が発行した値で**人が発明できない**。`source: 'auto'` を書くのは `tools/import-waitinglist.js` だけ（`recurring-dedupe.js` のヘッダも同じ事実に依存している）
- **効くのは各行につき1回だけ。**以後は控えが付くので自然に解消する
- **★★ここを `source: 'semi'` に広げてはいけない。** Instagram監視と画像取込みが書くのは `semi` で、**人が admin.html で入れた行と同じ source**。広げた瞬間に手入力572件が「機械のもの」に化けて静かに上書きされる。`machine-write-state.js` の `assertSeedSpec` が例外にして止める。**テスト5と6は対で維持すること**（6が無いと、seed を広げる変更が誰にも気づかれない）
- **無損失であることを実測で確かめてから入れた**: `git log <最新のbotコミット>..origin/main -- data.js` が空 ＝ 機械の最後の書き込み以降に人の編集が無い、を確認したうえで seed している。**このコマンドはマージ直前にもう一度実行すること**（非空なら、seed の前にその編集内容を確認する）

#### 機械に引き渡したいとき

**その行を消す**（`admin.html` の 🗑）。次の実行で機械が同じ枠に自分の行を入れる。専用の解除フラグは作っていない（社長に新しい操作を覚えさせないのが本件の目的のため）。

#### 検査は「保存則」ではなく【マージ前後の突き合わせ】

書き込み直前に3本の突き合わせを通す。**どれもマージ側のカウンタを一切参照しない** — 左辺はマージ前のディープコピー、右辺はマージ後の配列、それに控えだけで判定する。したがって `stats` を潰す変異（`protected` を数えない・`ok: true` に固定する等）が入っても**独立に生き残る**。

1. **機械のものでない行**は、マージ前に存在したものがすべて、内容そのままで残っていること
2. **人が直した項目**は、その行が残っている限り値が変わっていないこと
3. **人のものだった行が占めている枠に、機械の行を新しく置いていない**こと

**★3本目は変異試験で見つかった穴を塞いだもの（2026-08-04）。** 枠の保護を外す変異を入れても1と2は鳴らなかった。いまの実装は「置き換える」のではなく「書かない」ので、保護が外れると**人の行はそのまま残り、機械の行が1行増える**＝ **破壊ではなく重複**になるためである。重複も実害で、`recurring-dedupe.js` のヘッダが言うとおり「同じ大会が2行に見えるのは1行足りないより信用を損なう」。**検査が「破壊」しか見ていないと、この向きの退行を素通りさせる。**
- 誤検知しない理由: 見るのは**今回新しく増えた行だけ**で、既存どうしの同時刻衝突には触れない（実データには `v35` の `start:''` 同士のように正当な同枠の行がある）

**実測（複合変異）**: 枠の保護を外し、同時に `stats.protected` を数えないようにすると、サマリは `人の行を守って見送り 0件 / 追加 1件` と**正常に見える**。それでも3本目が発火して `rc=1` で書き込みを止め、人の行は1バイトも変わらなかった。

**カウンタで検算する形にしてはいけない。**同じ材料から導いた値どうしを比べると恒等式になり、何も検査しないものになる（この案件で4回踏んだ罠）。

行レベルの保存則には項を1つ足した。**「書かないと決めたその場で +1」しており、`取得結果の行数 - 書いた数` のような残差ではない**ので、この式は恒等式にならない。

```
Visionが返した行 = 追加 + 更新 + 変更なし + 過去日 + 破棄 + 不採用の投稿の行 + 【人の行を守って見送り】
```

#### 「鳴らない警報」を作らないための両方向テスト

この機能は**平常時なにもしない**ので、片方向だけ固定すると壊れていても気づけない。とくに「守る」側だけを置くと、**何もかも守る実装（＝自動取込が完全に死ぬ）がテストを全部通る**。

| 方向 | 何を固定するか |
|---|---|
| 守る | 人の行は1バイトも変わらない ／ 人が直した項目は残る ／ **翌日の実行でも残る**（2日ぶん実際に回す） ／ 突き合わせが書き込みを止める |
| **守らない** | **控えと一致する項目はちゃんと更新される** ／ **人の行が無い枠には機械の行が普通に入る** ／ seed された `wl-` の auto 行は更新される |

`machine-write-state.test.js` は**判定を潰す6通りの変異**（常に人のもの／常に機械のもの／食い違い無し／全項目食い違い／戻さない／全部戻す）で、いずれも2〜8本のテストが落ちることを実測してある。

さらに**取込み側も含めた12通りの変異**で、すべてテストが落ちることを確認済み（2026-08-04実測）。

| 変異 | 落ちたテスト |
|---|---|
| 枠の保護を外す ／ 同一idの保護を外す | 3 ／ 3 |
| 項目単位の保護を外す | 5 |
| seed の `source` 条件を外す ／ 接頭辞条件を外す | 1 ／ 1 |
| 控えに「人の値を戻した後」を書く | 71 |
| 突き合わせ1本目／2本目／3本目を無効化 | 4 ／ 3 ／ 1 |
| `stats.protected` を数えない ／ 保存則の `ok` を `true` 固定 ／ `protected` を残差で数える | 4 ／ 4 ／ 4 |

#### 状態ファイルが壊れた／消えたときの縮退（隠さずに書く）

控えが読めなければ全行が「控えなし」になる。すると

- **人の行は守られたまま**（控えが無い＝人のもの、が既定値のため）
- 機械の `auto` 行は seed で拾い直され、状態ファイル導入前と同じ挙動に戻る
- Instagram監視・画像取込みは**自分が前回書いた行を更新できなくなる**（新しい枠に足すだけになる）

つまり「人の行が壊れる」方向には劣化しない。ただし**機械の行に対する人の修正だけは、状態ファイルが健全な間しか守れない。** これは方式の限界であって、直したつもりで隠してはいけない。控えが読めなかったことは実行ログに必ず出る。

#### ⚠ `recurring-dedupe.js` との相互作用（`v22` / `v33` を有効化する人への申し送り）

`recurring-dedupe.js` が `RECURRING` の展開行を抑止する条件は「**`source:'auto'` の行と (venueId, date, 開始時刻) が完全一致**」。新しい規則では**人の行がある枠に `auto` の行を書かない**ので、その枠の `RECURRING` は抑止されず、**人の行と定期開催の行が2行並ぶ**可能性がある。

- **現時点の影響は0件**（2026-08-04実測）。`RECURRING` を持つ自動取込店は `v19` だけで、`v19` の未来日には手入力が1件も無い
- **`v22`（RECURRINGなし）/ `v33`（RECURRING 3件）を有効化するときは、生成後の店舗ページを実際に見て確認すること**（`v33` は未来日の手入力の有無も併せて見る）

### 書き込み直前の最終自己チェックと、過去日の並び順について（`tools/schedule-write-guard.js`）

`data.js` を書く自動経路（Waitinglist取込み / Instagram監視）は、書き込みの直前に「**取り込み対象の未来日以外は、何ひとつ動いていないこと**」を確かめる。破っていれば `data.js` を1バイトも書かずに中止する。この検査は**両ツールが同じモジュールを共有**している（同じ検査を2箇所に書いていた結果、まったく同じ欠陥が2つのツールに同居していた。下記リスク台帳 #17）。

#### 何を見て、何を見ないか

| 対象 | 増減 | 中身 | 並び順 |
|---|---|---|---|
| 対象外の店 | 見る | 見る | **見る**（緩めていない） |
| 対象店の過去日 | 見る | 見る | **見ない**（下記の理由） |
| 対象店の未来日 | — | — | — （取り込みが書き換える場所なので対象外） |

#### なぜ過去日の並び順だけ見ないのか

かつてこの検査は `JSON.stringify` で配列ごと比較していた。`JSON.stringify` は順序に敏感なので、**中身が1件も変わっていなくても並びが変わっただけで「過去日が変化した（バグ）」と報告して中止**していた。2026-08-04 の実データ試験（run 30922261347）がこれで止まっている。

並びが変わる理由は取り込みの中身とは無関係で、`data.js` の**配置**にある。各ツールの `mergeStore` は店の行を1か所のブロックに組み直して差し戻すが、その挿入位置（`insertAt`）は「その店の最初の行があった位置」で、**店の行が `data.js` 内で連続していること**を暗黙に前提にしている。実データは月末の一括登録（「THE DOJO: 2026年8月のトーナメント26件を登録」など）で月ごとに別の場所へ追記されるため、**1店が2ブロックに分かれる**ことが普通にある（2026-08-05 時点で11店）。マージがそれを1か所にまとめると、後ろのブロックにある過去日の行が**別の店の過去日の行を追い越す**。

この追い越しは、

- **抽出結果が0行でも起きる**（＝取り込みの中身に一切依存しない、構造上の挙動）
- **店ごとに一度きり**（一度まとめれば次回以降は0行。実測で確認済み）
- **ただし翌月分をまとめて登録するとまた分かれるので、月次で再発する**

順序の一致を不変条件にはできないので、**代わりに順序以外をすべて厳密に見る**。過去日の id の集合が完全に一致すること、同じ id の中身が1バイトも違わないこと、件数が一致すること（同じ行を2度書くバグは件数でしか捕まらない）。

#### 並びが変わった行数は毎回ログに出す

「順序を見ないことにした」で終わらせると、`data.js` の差分が数百行動いた理由を誰も説明できなくなる。**並びが変わった行数を毎回数えて出力する。0行でも1行出す**（変化したときだけ出す形にすると、出力そのものが壊れたときに静かに何も出なくなる）。

```
[monitor-instagram-apify] 過去日の並び: 4行の位置が変わりました(中身・件数は変わっていません)
[monitor-instagram-apify]   内訳: v18 3行 / v20 1行
[monitor-instagram-apify]   理由: data.js 内で行が2つ以上に分かれていた店を、マージが1か所にまとめたためです: v18(2ブロック) / v20(2ブロック) / v21(2ブロック)
```

数えるのは「**動かした行の数**」であって「添字がずれた行の数」ではない。1行が先頭へ移動すると後ろの行の添字は全部ずれるので、添字で数えると4行の移動が56行に化ける（実際 run 30922261347 ではそう見えていた）。

#### 並び順は掲載内容に影響するか — **「影響しない」とは書かない**

サイトは描画時に (date, start) で並べ替える（`index.html` / `tools/venue-schedule.js`）ので、配列順は基本的に表示に出ない。**ただし完全に無影響ではない。** 同じ (date, start) を共有する行どうしは比較が同値になり、**安定ソートによって入力順（＝配列順）がそのまま残る**。2026-08-05 時点の実データでは129枠が該当し、監視4店のマージで **634行中4行（2組）の表示順が入れ替わった**：

- `2026-08-04` v21「WJPT 祝勝会」 ↔ v20「FSTサテライト」
- `2026-08-19` v21「ディーラー ミナっち バースデートーナメント」 ↔ v20「フリーロール」

いずれも全店一覧での上下が入れ替わるだけで、**掲載内容そのものは同一**。店舗ページは単一店なので影響しない。

| **#35** | 人の行の保護を外す変異は「破壊」ではなく**重複**を生む。破壊しか見ない検査が素通りした |

**必ずやること（検査・保存則・警報を足す／共有モジュールに切り出すたびに）**：

1. **検知器の変異**（`ok` を `true` に潰す等）で落ちること
2. **★配線の変異**（検知器に値を渡す側＝カウンタの加算・記録の呼び出しを1本ずつ落とす）でも落ちること。
   **呼び出し側が複数あるなら、その全部に当てる**
3. **フィクスチャがその経路を実際に通っているかを先に確かめる**。
   #38 で抜けたのは検査ではなく**フィクスチャ**だった（「採用より新しい位置に非カレンダーが並ぶ探索」が無く、
   数えるべきカウンタが1件も動いていなかった）。**動かない項目は、壊しても落ちない**
4. **「実行時には正しく鳴る」で満足しない**。鳴ることを人が手で確かめても、
   **テストが落ちない限り退行は次のPRまで気づけない**

**共有モジュール化した検査は特に危ない** — 検査本体のテストは通るのに、**呼び出し側が呼ぶのをやめた**ことは
どのテストも見ていない、という形になりやすい（`recurring-dedupe.test.js` の冒頭コメントが同じ問題を扱っている）。

#### なぜ `assertOnlyTargetChanged`（過去日を順序込みで見る旧式）は残っていて平気なのか

`tools/tournament-merge.js` の `assertOnlyTargetChanged` は **PR #36 の修正を受けていない**（`JSON.stringify` で過去日を順序込みに比べたまま）。それでも #17 の形では鳴らない。**理由は「1店ぶんしか見ていない」から**：

- `mergeStore` が組み直すのは**その店のブロックだけ**で、`past` の**店内の相対順序は保たれる**（`[...past, ...sorted(future)]` の形で先頭に戻す）
- 対象外の店の相対順序も保たれる（`rest` の順序は触らない）
- 並びが変わるのは **「A店の過去日」と「B店の過去日」の間**だけ。`venueId` で絞ったこの検査には**構造的に見えない**

つまり **「複数店を1つの `targets` にまとめて見る検査」だけが #17 の発火条件を持つ**。実測でも 2ブロックの `v22` / `v27` / `v20` / `v18` / `v21` すべてで店ごとの検査は通過し、まとめて見る `checkNothingElseChanged` だけが（旧式なら）鳴った。**ただしこれは「直っているから安全」ではなく「見えていないから鳴らない」であり、`assertOnlyTargetChanged` の対象を複数店に広げた瞬間に #17 が再発する。** #18（`insertAt` の根治）に着手するまでは、**この関数に複数店を渡さないこと。**

#### 意図の根拠 — 「回復しない」検査はなぜそれでよいのか

| 群 | 回復しない理由 | 意図的だと判断した根拠 |
|---|---|---|
| W-1〜4 / **I-2** | 入力ファイルが壊れている。書き進めれば**壊れた `data.js` を本番に push する** | 落ちる先が公開サイトの白画面であり、止めるほうが軽い。ワークフローの `validate-data.js` ゲートと同じ考え方。**★ここに `apify-monitor-state.json`（旧 M-2）は含めない** — 壊れているのが `data.js` ではなく「どこまで見たか」の記録なので、空として続けても壊れたデータは公開されない（リスク台帳 #19） |
| W-6 / W-7 / M-3 / M-4 / **I-4** | **自分のバグを検出した**。中止しなければ人の入力を壊したデータが公開される | いずれも本文に「（バグ）。書き込みを中止します。」と書いてある。`data.js` を書かないことが目的そのもの |
| **I-3** | 同じ画像からは同じ結果しか出ない | 人が別の画像を渡すか手入力するのが正しい応答。日次経路は止まらない |
| W-8 / M-5 / **I-5**（トップレベル `catch`） | **回復するかは原因による**（＝この群だけは「回復しない」と断定できない） | 想定していない例外の受け皿。**握り潰さずに `exit(1)` で止める**のが目的で、原因が `data.js` の中身にあれば回復せず、外にあれば回復する |

**対照的に、落とさないと決めてある箇所もある**（同じ「状態ファイルが読めない」でも判断が逆）：

- `machine-write-state.js` の `readState` は、控えが壊れていても**例外を投げず空として続行する**。ヘッダに理由が明記してある — 「ここで落とすと状態ファイル1つで日次の取込みが永久に止まる」。空でも**人の行は守られる側に倒れる**（既定値が「人のもの」）ので、落とす利益が無い
- 実測でも `waitinglist-write-state.json` を壊した状態で `exit=0`・書き込み成功だった

#### ⚠ この監査で見つかった、**まだ直していない**点（起票のみ）

1. **`apify-monitor-state.json` が壊れると永久に止まる（M-2）のに、その性質がどこにも書かれていない。** 同じツールの中で、**もう一方の状態ファイル（`instagram-write-state.json`）は「落とすと永久に止まるから落とさない」と明記して落とさない設計**にしてある。同じ理由が効くはずの場所で判断が逆になっており、しかも逆にした理由が残っていない。**`apify-monitor-state.json` は bot 自身が毎日書いてコミットするファイル**（`git pull --rebase` の衝突・部分書き込みで壊れうる）なので、机上の話ではない。→ **リスク台帳 #19 として起票** → **2026-08-05 に解消**（落とさず「記録なし」として続行し、その実行の最後に書き直す。判断の理由・代償・実測は上の「確認済み投稿日時の記録が壊れたときの縮退」）
2. **書き込み前検査の失敗は、店単位の隔離を受けない（M-3a / M-3b）。** Instagram監視は「1店の取得失敗で全店を止めない」を設計の柱にしているが、**店ごとのループの中にある `assertOnlyTargetChanged` / `assertHumanEditsPreserved` は try/catch の外**にあり、2店目で鳴ると1店目までの取込みごと捨てて `exit(1)` する（実測で確認）。取得失敗だけが隔離され、検査失敗は隔離されない、という**非対称が文書化されていない**。→ **リスク台帳 #20 として起票**
3. **`tools/import-waitinglist.js` は `module.exports` を持たず、`main()` を無条件に実行する**（`require.main === module` のガードが無い）。他の2ツールにはガードがある。**このファイルを `require` すると、本物の `data.js` と本物のAPIに対して本番の取込みが走る。** 実際に一度事故になっている（調査のつもりで `node -e "require(...)"` を叩いた）。→ **リスク台帳 #21 として起票**

**この監査そのものでは1つも直していない。** 監査の目的は「回復しない検査を洗い出して記録すること」であり、直すのは別PRで正規のQAに掛ける。
**その後の状況（2026-08-05）**: **#19 は解消済み**（上記）。**#20 / #21 は起票のまま**。

### 半自動パイプライン（LINE / IG 等の埋め合わせ）

完全自動が無理なソースは、**告知テキスト/画像を渡す → LLMで正規化 → `data.js` に追記**で工数を最小化する。
Claude Codeのチャットで人手で行う場合(admin.htmlでの進捗管理)と、`tools/import-venue-image.js` で
CLIから行う場合の両方がこの型に当てはまる。

```
[店舗のLINE/IG告知テキスト・画像]
      │
      ▼
[LLM抽出]  date / start / name / buyin / addon / stack / guarantee / reentry / tags
      │  （下記スキーマに正規化）
      ▼
[レビュー(任意) → data.js へ upsert] → サイト反映
```

各トーナメントは `source`（`auto`/`semi`/`manual`）と `verified` を持つ。

> **⚠ `source` / `verified` はデータ側だけの項目で、現時点では画面に出していない（未実装）。**
> `index.html` にも `tools/venue-schedule.js` にも `t.source` / `t.verified` を読む箇所は無い。
> 実際に画面へ出ている信頼性の表示は **`lowConfidence` の「⚠ 要確認」バッジだけ**（一覧カードと店舗静的ページの両方）。
> なお `verified` は全609件が `false` のままで、「確認済み」を意味する運用も回っていない。
> 取得元のドット表示・「(未確認)」表記は**構想であって実装ではない**ので、実装済みだと誤解しないこと。

### Tournament スキーマ

```js
{
  id, venueId, name,
  date: 'YYYY-MM-DD', start: 'HH:MM',
  buyin: 円|null, addon: 円|null, stack: 点|null,  // null = 読み取れなかった（0 は「0円＝無料」の意味）
  guarantee: 円|null, reentry: true|'late'|false,
  prize: 文字列|null, tags: [],
  source: 'auto'|'semi'|'manual', verified: boolean,

  // 任意フィールド（無いときはキーごと出さない）
  lowConfidence: true,      // 目視確認が要る。Instagram監視では【参加費が大会名から推測された疑い】だけに付く
                            // （2026-08-04に判定を作り直した。上記「⚠ 要確認 の判定」）
  pinnedTags: ['ディープ'], // 人が固定したタグ。自動取込で上書きされず毎回 tags に合流する
}
```

`tags` は**表示に使う最終形**で、自動取込された店舗では毎回
「API由来タグ（`ターボ`/`ディープ`/`PLO`/`ミックス`） ＋ 人手タグ ＋ `pinnedTags`」で組み立て直される。
画面・静的ページの描画は `tags` だけを見ればよい（`pinnedTags` を直接読む必要はない）。

### タグ「大型」の定義

以下の**両方**を満たす場合のみ付与する。1店舗だけで完結する通常営業のトーナメント（各店舗のDAY1サテライト単体を含む）は、大きい大会の予選であっても対象外。

1. 次のいずれか
   - 複数店舗を巻き込んでサテライトが行われている**本線（決勝/本戦）**のトーナメント
   - 大会場を借りて実施する**イベント的な**トーナメント
2. 想定エントリー数が**最低100人以上**

### `実測` の語法（この台帳とREADME全体の約束）

**このリポジトリでは `実測` を一貫して「実データで観測した」の意味で使っている。** 実行ログ・`data.js` の中身・APIの応答など、**現実から数えた値**にだけ付ける語である。

**構成した想定標本に同じ語を当てないこと。** 品質管理部やレビュー部が「あり得る入力」として組み立てた集合は、どれだけ現実的でも**現実の分布ではない**。混ぜると「10通り中9通りが漏れる」のような数字が**実データの漏れ率**として読まれ、判断を誤らせる。

| 書き方 | 使う場面 |
|---|---|
| **実測** | 実行ログ・実データ・API応答から数えた値（例: 「2ブロックの店が11店」「未来日の GTD は5件」） |
| **品質管理部が構成した想定表現 / 想定標本** | 網羅性を確かめるために人が組み立てた集合（例: 休業表現24通り） |
| **無作為探索** | 生成した入力での探索（例: 「12万件で発火0件」）。**「発火しなかった」は「発火しない」の証明ではない**ので、必ず件数と生成条件を併記する |

**併せて、標本の限界も必ず併記する。** 例: run `30922261347` の閾値較正は「71投稿中28投稿を判定、43投稿は打ち切りの後ろで未確認」。**分母を書かない実測は、書いていないぶんだけ強く読まれる。**

## 法務・信頼性メモ

- フッターでは「当サイトは店舗・主催者が公開している情報を**集約する媒体**であり、賭博行為の勧誘・仲介を行うものではない」「賞品・プライズの取扱いは各店舗・主催者の規定による」と表明する。
  - 2026-07-22に、従来の「当サイトはアミューズメント(賭博性のない娯楽)目的の情報を掲載します」から変更した。
    旧文は**第三者である店舗・主催者のイベントの性質まで当社が保証する断定**になっており、賞金保証のある大型イベント(JOPT等)を掲載すると自社の表記と自社のコンテンツが矛盾するため。
    当社が保証できるのは「当社の立場」までであり、そこに限定する表現に改めた。
- **この文言を掲げる限り、参加受付・予約・エントリー代行・成果報酬型の送客は導入しない。** 導入を検討する場合は、先にフッター表記を見直しレビュー部の確認を通すこと。
  (旧文言が問題になったのは「書いた時点では正しかったが、事業の実態が動いて矛盾した」ため。同じ構造の再発を防ぐ。
  なお定額の店舗PR掲載枠・LINE配信は「広告」であって仲介ではないため、現行の文言と矛盾しない)
- 大型イベント特集ページには、非公式のまとめである旨・情報取得時点・当社の転記誤りの可能性を明示する免責を置く。
  賞金額を掲載する場合は、主催者発表である旨と、主催者側の建て付け(JOPTの場合「プライズは賞金ではなく選手契約」)を併記し、当社が言い換えない。
- **第三者である店舗の許認可状態(風営法の許可の有無等)を、当サイトの声で断定しない。** 店舗自身が公開している言明を載せる場合は「公式サイトによると」等で帰属を明示する。
  - 2026-07-29、行橋の POKER Studio DEEP BLUE の掲載時に定めた。当初は公開noteに「風営法5号許可取得」と当サイトの断定として書いていた。
    許可の有無は公安委員会の処分であって当社に確認手段がなく、誤っていた場合は
    (1)利用者が店舗の法的地位を誤認する (2)保有していない許可を当サイト発で公表された店舗が実害を被る (3)当サイトの正確性が損なわれる、の3方向に影響が出る。
    **当社が保証できるのは「店舗がそう表明していること」まで**という、フッター文言と同じ考え方を店舗情報にも適用する。
- **「県内初」「エリア初」等のNo.1表現も当サイトの断定にしない。** 「〜とされる」「公式サイトが〜を掲げる」と伝聞・引用の形にする。
  - 景表法上の表示主体は原則として供給者(店舗)だが、当社は定額の店舗PR掲載枠を扱うため、将来それと結びついた場合に合理的根拠の議論に接続しうる。先回りして断定を避ける。
- **出典は「どのページの、どの記述か」まで `fukuoka-venues.json` の `note` に記録する。** 店舗公式サイトのトップページ・運営会社の会社概要・第三者媒体では、同じ文言でも重みが異なる。

    (実際の根拠は店舗公式サイトのトップページにある店舗自身の言明だった)。**出典URLを列挙するだけでは、次に読む人が同じ取り違えをする。**
- **根拠の弱い情報は、公開面(`data.js` の `note`)でもその旨をヘッジする。** 「住所は未確認。」「住所は第三者情報のため要確認。」等。
  内部の `fukuoka-venues.json` にだけ留保を書いて公開面に落とさないと、読者は確度の差を知らないまま行動する(部屋番号まで載せた住所が誤っていれば、無関係な入居者の部屋を訪ねることになる)。
