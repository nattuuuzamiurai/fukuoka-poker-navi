# ふくおかポーカーナビ（福岡ポーカートーナメント日程アグリゲーター）

福岡県内のアミューズメントポーカー店のトーナメント日程を一括表示する公開サイト。
エースハイ合同会社の収益プロジェクト v1。

## これは何か / 収益設計

- **資産になる「サイト」を母艦**にする（SEO：「福岡 ポーカー トーナメント 日程」等）。
- **LINE公式 / X**は無料の通知・回遊チャネルとして**サイトへ送客**（収益はサイト側）。
- 収益スロットは3層を最初から埋め込み済み：
  1. **広告（AdSense）** … `.adslot` の位置。PVが付けば自動で回る。
  2. **店舗のPR/有料掲載** … `venue.featured = true` でカード上部固定＋「PR」バッジ＋★。単価が高い本命。
  3. **周辺商品アフィリ** … 記事/サイドに随時追加（今後）。

### 自社広告カード（ポーカートナメ成績表）の3か所

AdSense/PR枠が埋まるまでの間、自社アプリの導線を3か所に置いている。**それぞれ狙いと太さが違う**ので、
1か所を触るときに他をつられて変えないこと。

| 場所 | セレクタ | 高さ(375px) | 備考 |
|---|---|---|---|
| トップ（大型バナーの**上**） | `.adslot .adCard` | 約100px | **位置は変えない**（社長判断。バナー下への移動案は却下済み）。上に積み上がる要素なので**意図的に薄くしてある**（社長指示・2026-07-29。元は約200px） |
| ページ下部 | `main > .adCard` | 約206px | 読み終わり地点なのでフルサイズのまま |
| 画面下固定 | `.stickyAd` | 約57px | 全ページ共通の常時表示 |

トップだけを薄くするために CSS を `.adslot` 配下に限定している。`.adCard` の共通ルールを直接いじると
下部カードまで薄くなるので注意。

薄くするのは**寸法（余白・画像・ボタン）を詰めて**行うこと。
トップは最も露出の多い枠なので、**「buyin・順位・収支を記録できる」という"何ができるアプリか"の訴求は文言から落とさない**
（高さ稼ぎに説明文を削ると CTR に直接効く）。320px級で見出しが3行に折り返す場合も、文言ではなく
`@media(max-width:360px)` 側の寸法で吸収する。

### `data.js` を更新したら（月次の日程入力のあと・店舗を追加したあと）

```
node tools/gen-venue-pages.js .          # 店舗ページ35枚 + トップの店舗リンク行 + sitemap.xml
```

をリポジトリのルートで実行し、**生成物もコミットする**（GitHub Pages は静的配信なので生成物が必要）。
ズレていないかだけ見たいときは `--check` を付ける（書き込まず、一致しなければ非ゼロ終了）。

> **人が `data.js` を触ったときの話**。Waitinglist の日次自動取込で `data.js` が変わったぶんは、
> ワークフローが同じジョブの中で再生成するので手作業は要らない（下記「Waitinglist 自動取込」）。

- 店舗ページの日程は**「生成時の静的レンダリング＋閲覧時に `data.js` から再描画」のハイブリッド**。
  そのため再生成を忘れても**閲覧者には最新が出る**が、**JSを実行しないクローラには古い日程が見えたまま**になる。
  「画面で見えているから大丈夫」は成り立たないので、`--check` で機械的に確認すること。
- 静的側に焼き込むのは「実行日から先」ではなく **`data.js` に載っている期間そのもの**。
  実行日に依存させると、データを1文字も触っていないのに翌日には `--check` が落ちて検査が信用できなくなるため。
- **焼き込む期間は店舗ごとに独立している**（`tools/venue-schedule.js` の `venueRange()`）。
  その店の日付つきトーナメントの範囲を月単位に丸めたものを使うので、**ある店に1件足しても
  他店のページは1バイトも変わらない**。見出しの「〇月〜〇月の掲載分です」もその店の実データと一致する。
  - 以前は data.js 全体の最小日〜最大日を全店で共有していたため、1店に1件足しただけで35ページが書き換わり、
    9月分を持つのが1店だけでも他34店に「7月〜9月の掲載分です」と出て9月の定期開催行まで焼き込まれていた
  - **定期開催（`RECURRING`）しか無い店**はその店由来の日付が無いので、代表として
    「サイト全体の掲載期間の先頭1ヶ月」を焼く（毎週繰り返すので1ヶ月あれば全曜日が出揃う）。
    ここを最終日側にすると、どこかの店に来年の大会が1件載っただけでページが数倍に膨らむ
  - **日付つきも定期開催も無い店**は期間そのものを出さない（見出しは「トーナメント日程」だけ）。
    1行も載っていないのに「この一覧は〇月〜〇月の掲載分です」と書くのは事実と合わないため
- **閉店・掲載終了で `VENUES` から店を削除したときも、必ず再生成する。**
  再生成すると `data.js` に無くなった `venues/<slug>/` は**削除される**（対象名を表示する）。
  消さないと、閉店店舗の `LocalBusiness` 構造化データ付きページが更新されないまま公開され続ける
  （sitemap から消えるだけではインデックスは落ちない）。`--check` は孤児が残っていると非ゼロ終了する。
  なお `index.html` 以外のファイルを手で置いたディレクトリは自動削除せず、名前を出して止まる。
- イベントデータ（`jopt-data.js` / `big-events.js` 等）を変えたときは `node tools/gen-event-pages.js .` も実行する。

### `sitemap.xml` の所有者

`sitemap.xml` に載るURLは **`big-events.js`（イベントページ）と `data.js`（店舗ページ）の2つ**にまたがる。
両方の生成スクリプトがそれぞれ自前で組み立てると「後に実行したほうが相手のURLを消す」奪い合いになるため、
**中身を決める場所は `tools/gen-sitemap.js` だけ**にしてある。
`gen-event-pages.js` と `gen-venue-pages.js` は `sitemapFile()` を呼んで返ってきた文字列をそのまま書くだけで、1行も組み立てない。

- 入力が同じなら出力は同じ文字列なので、**どちらをどの順に何回実行しても内容は変わらない**
- **片方を実行し忘れてsitemapが古くなることもない**（どちらを実行しても全URLが揃う）
- `changefreq` / `priority` は**日付で変えない**。終了した大会を低優先度に落とす分岐を入れると
  「データを触っていないのに翌日 `--check` が落ちる」ことになるため。この2項目はクローラへの弱いヒントに過ぎない

## 大型イベントの追加手順と掲載期間ルール

大型大会（WJPT / JOPT / FST など）は**基本的にWJPTと同じ掲載の仕方をする**（社長の恒久ルール）。
つまり **トップページのバナー ＋ サイト内の専用ページ（`#<id>`）** の2点セットで載せる。

### 掲載期間ルール（社長指示・2026-07-29）

判定は `big-events.js` に**一本化**されており、日付比較を各所に書き足してはいけない。

- **掲載開始日 = そのイベントの初日 − 14日**
- **掲載終了日 = そのイベントの最終日 + 1日**（その日は含む）
  - 大型大会は日付を跨いで進行することがあるため、最終日の翌日までは載せ続ける
- 各イベントの掲載ウィンドウは**他のイベントを一切参照せず独立**して決まる。したがって
  **掲載期間は重なってよく、トップのバナーは同時に複数件出る**（社長了承済み）
- 逆に、どのウィンドウにも入らない期間は**バナー0件**になる（現在の登録内容だと 2026-08-18〜09-04）。
  これは仕様であってバグではない。埋めようとしないこと

> **【重要】掲載ウィンドウと「開催中/終了」の判定は、しきい値が意図的に1日ずれている。**
> 掲載ウィンドウは *最終日+1* まで、開催中/終了の判定（`isEventArchived()`）は *最終日* まで。
> つまり**最終日の翌日は「バナーは出るが、終了状態（暗転＋「終了」バッジ）で表示される」**のが正解。
> 社長の言葉:「掲載してほしいだけで次の日はバナーは終了でいいです」。**揃えないこと。**

現在の登録内容だと掲載期間はこうなる：

| 大会 | 会期 | 掲載開始（初日−14日） | 掲載終了（最終日+1） |
|---|---|---|---|
| WJPT | 2026-07-18〜07-20 | 2026-07-04 | 2026-07-21 |
| JOPT | 2026-07-30〜08-02 | 2026-07-16 | 2026-08-03 |
| NIPPON SERIES | 2026-08-11〜08-16 | 2026-07-28 | 2026-08-17 |
| FST 5.0 | 2026-09-19〜09-23 | 2026-09-05 | 2026-09-24 |

### どこに何が出るか

| 場所 | 何件 | 判定関数 |
|---|---|---|
| トップのバナー | 掲載ウィンドウに入っているもの**全件**（0〜複数）。並びは 開催中 → まもなく（初日の近い順） → 終了 | `visibleBigEvents()` |
| フッターの「大会特集」 | **1件**。開催中があればそれ（複数なら最終日が早い方）、無ければ次の大会（初日が最も近い未来）。どちらも無ければ行ごと非表示 | `footerBigEvent()` |
| 大型一覧（`#majors`） | 未開催・開催中は全件、終了済みは**新しい順に3件まで**（暗転表示）。それより古い大会は出さない | `bigEventListForIndex()` |

**フッターは掲載ウィンドウに縛られない**（バナー0件の期間でも「次の大会」を出し続ける）ため、
バナーとフッターが一致しない日がある。これも仕様。
静的ページ（`events/<slug>/`）のフッターも同じ `big-events.js` をブラウザ側で実行して判定するため、
ページを再生成しなくても掲載中の大会が自動で切り替わる（生成時に焼き込まない）。

#### フッターは「恒久リンク行」と「大会特集」の2本立て（消さないこと）

**トップページ（`index.html`）と静的ページ（`events/<slug>/`）の両方**のフッターに、
**役割の違う2行**が入っている。**片方を理由にもう片方を消さないこと。**

| 行 | 中身 | 目的 |
|---|---|---|
| 恒久リンク行 | レジストリの**全大会**（会期の古い順） | **SEO**。静的イベントページへのクロール経路・内部リンク評価。**日付で消えてはいけない** |
| 大会特集 | **その日の1件**（`footerBigEvent()`） | 回遊。該当が無ければ行ごと非表示 |

リンク先は各エントリの `featureUrl`。静的ページを持つ大会はその静的URL、
持たない大会（FSTなど）はハッシュURL（`/#fst`）になる。

恒久リンク行は**トップも静的ページも `tools/gen-event-pages.js` が生成する**（**どちらもJSなしのHTMLに
実リンクが載る**のが要点）。出どころは `permanentEventLinks()` ただ1つで、**手で書き足す場所はない**:

| ページ | 生成方法 | レジストリに足したとき |
|---|---|---|
| `events/<slug>/` | `permanentEventLinks()` がページ全体と一緒に焼き込む。自分自身は `aria-current="page"` でリンクにしない | **生成スクリプトの再実行だけ**で増える |
| `index.html`（トップ） | 同じ `permanentEventLinks()` が **`<div id="evtLinks">…</div>` の1行だけを上書き**する（`index.html` の他の箇所には触らない）。実行時には `mountBigEventLinks()` が同じ内容で描き直す | **生成スクリプトの再実行だけ**で増える |

**ズレを検知する仕組み（覚えておく必要をなくすため、3重にしてある）**

| 仕組み | いつ効くか | 何が起きるか |
|---|---|---|
| `node tools/gen-event-pages.js <repo>` | 大会を追加したとき | トップと静的ページの**両方**が同時に更新される（片方だけ、が起こらない） |
| `node tools/gen-event-pages.js <repo> --check` | レビュー時（手動） | 書き込まずに突き合わせ、1文字でも違えば**非ゼロ終了**して落とす |
| `mountBigEventLinks()` の自己点検 | ブラウザで開いたとき（初回描画時） | HTMLの静的リンクがレジストリとズレていたら**コンソールに警告**を出す |

> 過去に「大会特集は1件」という指示を取り違えて恒久リンク行ごと削ってしまい、
> 全大会が終了した日以降に内部リンクがゼロになる状態を作ってしまったことがある
> （静的ページ側・トップ側で2回）。「1件」なのは**大会特集の行だけ**であって、内部リンクの話ではない。
> さらにその直後、**静的ページだけ直してトップを見落とす**という取りこぼしも起きた。
> ズレていても `mountBigEventLinks()` が描き直すので**画面上は正常に見え、目視では気づけない**
> （欠けるのはJSを実行しないクローラに対してだけ）。上表の仕組みはこの見えない壊れ方への対策。

**CIは現時点で未実装**（`.github/workflows/` は無く、`--check` は人が手で走らせている）。
将来CIを組む担当への注意が2点ある。

1. **`<repo>` は相対パス（`.` など）でも絶対パスでも動く。** 3つの生成スクリプトはいずれも
   受け取ったパスを `path.resolve()` で絶対パスに直してから `require()` する。
   ```sh
   node tools/gen-event-pages.js . --check                      # ← 相対パスでも動く
   node tools/gen-event-pages.js "$GITHUB_WORKSPACE" --check    # ← 絶対パスでも動く
   ```
   かつて相対パスで落ちていた（`require(path.join('.','jopt-data.js'))` が `jopt-data.js` という
   ベアモジュール指定に正規化され、Nodeがインストール済みパッケージとして探して失敗した）。
   **新しく生成スクリプトを足すときは、受け取ったパスを必ず `path.resolve()` すること。**
2. 上表の3つは**役割が違う**ので、CIを入れても `mountBigEventLinks()` の自己点検は残すこと
   （CIはコミット時点のズレ、自己点検は実際に配信されたHTMLのズレを見ている）。

### トップのバナーの見せ方（社長指示・2026-07-29）

掲載が複数件になっても**縦には積まない**。縦積みだとバナー1件につき約195px、直下の
「トーナメント日程」見出しが押し下げられ、ファーストビューから日程が消えてしまうため。

| 件数 | 見せ方 |
|---|---|
| 0件 | 領域ごと非表示（`#bigEventBanner:empty`） |
| 1件 | バナー1枚。**カルーセルUI（ドット・矢印）は出さない** |
| 2件以上 | **横スライド（カルーセル）**。縦の占有は常にバナー1枚分 |

実装は `index.html` の `renderBigEventBanner()` / `initBigEventCarousel()`（CSSは `.evtCarousel` 系）。
**外部ライブラリは使わない**（このサイトは依存ゼロで動いている）。ネイティブの横スクロール＋
CSS `scroll-snap` だけで作ってあり、レジストリに大会を足せば枚数は自動で増える。

「スライドできる」と伝えるための仕掛けは次の4点セット。**どれか1つを外すと伝わらなくなるので削らないこと**。

1. **次の1枚の端をちら見せ（peek）** — スライド幅を `86%` にして右に次が覗く（375px幅で約38px）。最重要。
   ただし**スライドが必要なときだけ**の仕掛けで、全部が一度に収まる幅（下記）では peek は無くなる
2. **ドットインジケーター** — 枚数と現在位置。現在のドットは横長のバー状に強調
3. **左右の矢印ボタン** — `min-width:720px` かつスクロールが必要なときだけ表示（タッチ環境はスワイプが自然なので補助扱い）
4. **初回のヒントアニメーション** — 一瞬だけ横に動いて戻る。`prefers-reduced-motion: reduce` では**必ず無効**

#### 720px以上では「スライド」ではなく「横並び」になる（2件のとき）

バナー画像は 1024×412（約2.5:1）なので、**スライドを横に広げるほど縦に伸びる**。幅いっぱいまで
伸ばすと1枚で高さ390px前後になり、直下の「トーナメント日程」見出しがファーストビューから外れる。
そこで **720px以上ではスライド幅に上限を掛けて**、2枚が横に並ぶようにしている。

| 幅 | スライド幅の上限 | 実測（2件時・スライド幅 / バナー領域の高さ / 見出しY） |
|---|---|---|
| 〜719px（モバイル） | なし（`flex:0 0 86%`） | 375px: 295px / 191.7px / **669** |
| 720〜999px | `calc((100% - var(--ec-gap)) / 2)` | 768px: 363px / 201.0px / **637**　999px: 478.5px / 247.5px / **683** |
| 1000px〜 | `470px`（トラック幅は常に968px） | 1280px: 470px / 244.1px / **680** |

- `--ec-gap` は `.evtCarousel` に置いたスライド間の余白（10px）。**gapの数字を2箇所に書かない**ための変数
- 全部収まると JSが `.ec-fits` を付け、**矢印とドットを消す**（動かないのに操作UIがあると誤解を招くため）
- 3件以上に増えれば収まらなくなり、**自動でスライド表示に戻る**（判定は `track.scrollWidth <= clientWidth` の実測。枚数や画面幅を決め打ちしない）

> **この上限は「2枚が丸ごと収まる幅になる値」でだけ掛けること。**
> 中途半端な固定値（例: 520px）で掛けると、2枚目が大きく覗くのに最後まで見えず、
> **「日程を見る →」ピルが縦に真っ二つ**になる。実際に一度その状態でレビューに出して差し戻された。
> 720〜999pxを `calc((100% - gap) / 2)` という**相対値**にしているのはこのため
> ―― 2枚＋gapがトラック幅に必ず一致するので、「途中で切れる幅」が原理的に発生しない。
> 変更したら **320〜1960pxを1px刻みでスイープし、CTAの部分表示がゼロ**であることを実測で確認する。

> **モバイル（〜719px）には手を入れないこと。** 画面が狭く2枚を並べる余地がないうえ、
> 見出しYの現行値（320px=469/640/642、375px=477/670/669、390px=477/676/674、414px=477/686/682。
> それぞれ0件/1件/2件）が社長・レビュー確認済みの基準になっている。

**やってはいけないこと**

- **自動スライド（オートプレイ）を足すこと。** トップの自動スクロールはコミット `6f9eddb` で意図的に廃止済み
- **ページ全体に横スクロールを出すこと。** 横に流れるのは `.ec-track` の内側だけ（320px / 375px で
  `document.scrollWidth === clientWidth` を必ず確認する）
- **大型一覧（`#majors`）を横スライドにすること。** あちらは一覧なので縦並びのままが正しい

「完全自動」はソースによって可否が分かれる。**取れるものは自動、取れないものは半自動**のハイブリッドにする。

| ソース | 自動化 | 方法 |
|---|---|---|
| **Waitinglist（DMMポーカー）掲載店** | ◎ **自動（稼働中）** | 認証不要の公開JSON APIを毎日取得 → `data.js` に upsert（下記） |

### Waitinglist 自動取込（`tools/import-waitinglist.js`）

DMMポーカーのイベントカレンダーは Waitinglist の埋め込みで、その裏に**認証不要の公開JSON API**がある。
これを使って掲載店のトーナメント日程を毎日自動取得する。**手入力ゼロで日程が最新化される唯一の経路**。

```
GET https://api.waitinglist-poker.com/v1/game-schedules/tournament?storeId=<storeId>&limit=100&page=1
    User-Agent: fukuokapoker.com-bot/1.0 (+https://fukuokapoker.com/contact.html)
→ { totalRecords, tournaments: [...] }   ※limit最大100・pageは1始まり。ページ間は1秒あける
```

- **取得のマナー（方針）**: **ブラウザを詐称しない。** 実体は GitHub Actions から1日1回動く当サイトのボットなので、そのとおり名乗り、問い合わせ先（`contact.html`）をUAに含める。相手側が「これは何者か」を確認して、遮断したい・連絡したいと思ったときにそれができる状態にしておくため。
  - 調査時は `Origin: https://poker.dmm.com` / `Referer: https://poker.dmm.com/` とブラウザのUAを付けて叩いていたが、**外しても同じ HTTP 200 で同じ件数が返る**ことを確認したうえで削除した（2026-07-31検証）。認証もトークンも不要な公開エンドポイントで、`api.waitinglist-poker.com` と `poker.dmm.com` のどちらにも `robots.txt` は存在しない（404）
  - 1日1回・ページ間1秒・対象1店舗（105件を2リクエスト）で、相手の負荷は無視できる範囲に収めている
- **実行**: GitHub Actions `.github/workflows/import-waitinglist.yml` が**毎日 06:23 JST**（cronは `23 21 * * *` UTC）に実行。手動実行（`workflow_dispatch`）も可。差分があるときだけ `github-actions[bot]` がコミット＆プッシュする（push直前に `git pull --rebase` して、checkout〜pushの間に main が進んでも静かに止まらないようにしている。この `git pull --rebase` がマージベースを解決できるよう、`actions/checkout` は `fetch-depth: 0`＝浅いクローンにしない）
- **対象店舗**: スクリプト冒頭の `STORES` 配列で管理。**1行足すだけで店舗を増やせる**。現在有効なのは `v3` のみ（他はコメントで控えてある）

  | venueId | storeId | data.js の店名 | APIの店名 | 状態 |
  |---|---|---|---|---|
  | `v3` | 4018492 | m HOLD'EM 中洲 | m HOLD'EM 中洲 | **有効** |
  | `v22` | 4012445 | CRownCLown（クラウンクラウン） | CRownCLown | 控え（名称一致・すぐ有効化可） |
  | `v19` | 4039056 | CASINO Arrows 小倉店 | CASINO Arrows 小倉店 | 控え（名称一致・すぐ有効化可） |
  | `v27` | 4069478 | THE DOJO | THE DOJO | 控え（名称一致・すぐ有効化可） |
  | `v33` | 4091897 | Poker room SKY | Poker room SKY | 控え（名称一致・すぐ有効化可） |
  | `v26` | 4009265 | JOKER♠️ 福岡大橋 | **POKER HOUSE JOKER** | ⚠ **要確認**（店名が一致しない。同一店か未確認） |
  | `v30` | 4050814 | ARIA 中洲 | **Aria**（登録1件のみ） | ⚠ **要確認**（店名が一致せず掲載も1件のみ） |

  ⚠ の2店は**有効化する前に人間が同一店舗かを確認すること**。venueIdを取り違えると、よその店の日程を掲載してしまう（スクリプト側の店舗同一性チェックは storeId の取り違えを検出できるが、「storeIdは正しいがvenueIdの割り当てが間違っている」は検出できない）。

- **マッピング**: `startAt`(UTC) に +9時間して JST の `date`/`start` にする。`buyin`←`registrationFee`、`stack`←`startingStack`、`reentry`←`entries` に `reEntry` があるか、`tags`←`feature`(ターボ/ディープ) と `gameRule`(plo→PLO / mix→ミックス)。`id` はAPIのULIDを使い `wl-<id>`（安定・冪等）
- **`addon` の注意**: `addons[]` は「アドオン」専用の配列ではなく、**リバイや参加費違いの枠も混ざっている**（例: `m GLORY` の `addons[0]` は `addonName: "リバイ"`、`m Brain ~LONG EDITION~` には `"30,000pt持ち"` が入る）。`addons[0]` をそのまま使うと**リバイ料金を「+AO」と誤表示する**ため、`addonName` が「アドオン」/`add-on` にマッチするものだけを採用している
- **意図的に埋めないもの**: `guarantee` / `prize` はAPIに該当フィールドが無く、`notes`（長文の告知テキスト）からの正規表現推測は誤りの温床なので**APIからは埋めない**。`大型` タグも定義上人間の判断が要る（後述「タグ「大型」の定義」）ため**自動付与しない**。名前からのタグ推測も行わない（誤タグを撒かないことを優先）
- **人手情報の引き継ぎ**: APIが供給できない情報（`guarantee` / `prize` / `pinnedTags` / 人が付けたタグ）は、置き換え・再生成のたびに**既存エントリから引き継ぐ**。上書きしてよいタグ語彙は API 由来の `ターボ / ディープ / PLO / ミックス` だけで、`バウンティ` `特別開催` `サテライト` `大型` などは温存される。これが無いと、人が後から足したGTDやタグが翌朝の自動実行で消える
  - **同じ (date, start) にAPI側が複数あるとき**は、どの大会の情報か特定できないため**名前が一致する手入力からのみ**引き継ぐ（一致しなければ引き継がない）。GTDを両方に配って「GTD 100万」のカードが2枚並ぶ方が、欠落よりも害が大きいため。見送った件数は実行ログに出る
- **`pinnedTags`（人手で固定するタグ）**: **`pinnedTags` が必要なのは `ターボ / ディープ / PLO / ミックス` の4語だけ**。この4語は毎回APIの `feature`・`gameRule` で上書きされるため、`tags` に手で書いても翌日消える。人の判断でこの4語を足したいときは `pinnedTags` に入れる。`carryOver` が GTD・プライズと同じく引き継ぐため、毎日の再生成後も残る
  - **それ以外のタグ（`バウンティ` `特別開催` `サテライト` `大型` `フリーロール` `リーグ` など）は `tags` に直書きすれば保持される**。`pinnedTags` に入れる必要はない（入れても動くが、「APIと競合するので固定した」という意図が読めなくなるので使わないこと）
  - `tags` は毎回「API由来タグ ＋ 人手タグ ＋ `pinnedTags`」で組み立て直される（描画側は `tags` を見るだけでよく、変更は不要）

  ```js
  // 例: ｍ Hyper Deep Turbo（feature は「ターボ」だがスタック10万点で実質ディープ）
  { …, "tags": ["ターボ", "ディープ"], "pinnedTags": ["ディープ"] }
  ```

  空のときはキーごと出力しない（`lowConfidence` と同じ任意フィールド扱い）。
  **なぜ自動判定にしないか**: APIの `feature` は単一値で「ターボかつディープ」を表現できず、さらに欠測もある（`m WTB Turbo` は `feature` が無く、名前にTurboとあるのにターボが付かない）。`startingStack` からの推測も、ノーマルとディープの両方に 40,000 が出現するため閾値では分けられない。特定の大会に合わせたマジックナンバーは他店に広げた瞬間に破綻する。そこで**自動判定を増やさず、人が付けたことがデータ上わかる形**で残す設計にした
- **upsert規則**（データ喪失を起こさないための取り決め）
  1. **過去日（JST基準の今日より前）のエントリは一切触らない**
  2. 対象店舗の `source: 'auto'` の今日以降のエントリは毎回作り直す（APIから消えた＝中止の場合はそのまま消える）。ただし上記のとおり人手情報は引き継ぐ
  3. 手入力（`semi`/`manual`）のうち **API側に同じ (date, start) があるもの**はAPI版に置き換える（APIの方が stack/addon/reentry まで持ち情報が richer なため）。このときも手入力側の GTD・人手タグは引き継ぐ
  4. 手入力のうち **API側に対応が無いもの**は残し、件数と内訳をログに出す（APIに未登録なのか中止されたのか人間が判断できるように）
  5. 対象店舗以外・`VENUES`・その他の定数には一切触らない。店舗ブロックの位置は保ち、ブロック内は date → start 昇順
- **安全弁**: 「HTTP 200が返ってきたから正常」とは扱わない。次のいずれかで `data.js` を**書き換えずに非ゼロ終了**する（＝ワークフローも失敗する）
  1. fetch失敗 / HTTP 200以外 / レスポンス形状が想定外
  2. 対象店舗の取得件数が **0件**
  3. **ページング不整合** … `totalRecords` に対して**重複排除後の**実取得件数が足りない（2ページ目が空で返る／同じidが水増しされている／ページング中のレコード挿入で同一レコードが2ページに跨る、等）。排除“前”の件数で判定すると、重複で嵩上げされたぶんだけ実データが静かに欠ける
  4. **別店舗の混入** … `store.displayId` が**無い**、または要求した `storeId` と違うレコードが1件でもある（フィールドが落ちているだけで検証がスキップされないよう、存在自体を必須にしている）
  5. **今日以降の件数の急減** … 部分障害（数件しか返らない・過去日しか返らない等）を検出する。**「前回の半分未満」（比率）と「1回で10件以上の減少」（絶対値）の両方**で見る。比率だけだと件数が多い店ほど1回で大量に消せてしまうため。閉店・長期休業など正当な減少のときは `--allow-shrink` を付けて人が明示的に通す
  6. 書き込み直前の自己チェック … 「対象外店舗のデータが変化していないか」「過去日のエントリが変化していないか」

  一時的なネットワークエラーは最大3回までリトライする。加えてワークフロー側でも、コミット前に `data.js` の構文・件数（500件未満なら異常）・id重複を検証する
- **確認用**: `node tools/import-waitinglist.js --dry-run` で書き込まずに差分サマリだけ出せる。実行時は必ず `追加 / 更新 / 変更なし / 削除 / 手入力の置き換え / API未掲載の手入力` の件数を出力する
- **静的ページの再生成もこのワークフローの中でやる**: 自動取込で `data.js` が変わると、そのスナップショットである `venues/<slug>/index.html` と `sitemap.xml` が古くなる（閲覧者にはブラウザ側の描き直しで最新が出るので、**画面を見ても気づけない**）。そこで `import` → 妥当性確認のあと、コミット前に `node tools/gen-venue-pages.js .` と `--check` を実行する。**自動取込ぶんについて人が再生成する作業は無い**。
  - 焼き込む期間が店舗別（`venueRange()`）になったので、**日次で書き換わるのは `data.js` と取込対象店のページだけ**。実測（v3に1件追加 / v3の9月分が消える / 2027年3月の大会が1件載る の3シナリオすべて）で**2ファイル**（`data.js` + `venues/m-holdem-nakasu/index.html`）に収まり、他店のページと `sitemap.xml` は動かない
  - 全店共通の期間だった頃は、同じ3シナリオが **2 / 36 / 36 ファイル**、`venues/` 全体が 1.1MB → 1.4MB（`casino-bar-leje-hakata` 単体で 61KB → 142KB）まで膨らんでいた。無人の日次pushでこれをやると `venues/` を触る他の作業と競合が常態化する
- **自動取得の対象店リストを出力する**: 実行のたびに `STORES` の内容を `auto-import-stores.json`（リポジトリ直下）に書き出す。**掲載管理コンソール（別リポジトリ `fukuoka-poker-admin`・ローカル専用）が読んで「この店は自動取得なので手入力不要」を出す**ためのもの。コンソール側がこのスクリプトの JavaScript をパースしなくて済むようにしてある。
  - 中身は `STORES` から取れる値だけで、**生成日時などの毎回変わる値は入れない**。入れると日程に変化が無い日でもこのファイルだけが差分になり、日次実行のたびに無意味なコミットが増える（ワークフローの差分判定は `git status --porcelain` なので1バイトでも変われば必ずコミットされる）
  - `STORES` を編集したら `node tools/import-waitinglist.js` を実行して**このファイルも一緒にコミットする**。忘れても翌朝の日次実行で更新される。`--dry-run` を付けると書き込まずに「ズレているか」だけを報告する
  - 途中で異常を検知して中止した実行では書き換えない（`data.js` と同じく、失敗した実行は何も残さない）
- **⚠ 運用メモ**: GitHub Actions のスケジュール実行は、**リポジトリが60日間まったく活動しないと自動的に無効化される**（GitHubの仕様）。無効化された場合はActionsの画面から手動で再有効化する。このワークフロー自身が差分をコミットするため通常は活動が途切れないが、日程に変化が無い期間が続くとコミットが発生しない点に注意

### Instagram自動巡回は中止し、店舗からの画像直送＋Vision取込みに切り替えた(2026-07-31)

公式サイトAPIが無い店舗(v40/v20/v18/v21/v34/v35)向けに、PR #13で「社長個人アカウントの
セッションCookieでInstagramにログインし、フィードを巡回して新着投稿を検知する」仕組みを実装したが、
**セッションCookie注入＋検知回避を伴う設計だったため、経営管理オフィスの判断で中止した。**
ログイン・巡回・ブロック回避のロジック(`instagram-browser.js` / `sns-schedule.js` /
`sns-monitor-instagram.js` / GitHub Actionsの定期実行ワークフロー)はいずれも採用していない。

代わりに、**各店舗に「Instagramへ投稿する月間スケジュール画像を、当社のLINE/メールにも直接送ってもらう」
運用に切り替えた。** これによりInstagramへの自動アクセスは一切不要になり、届いた画像を
`tools/import-venue-image.js` で取り込むだけの通常のツール運用になる。

```
[店舗がLINE/メールでスケジュール画像を直接送付]
      │  (人が画像ファイルを保存する。メール受信の自動化は対象外)
      ▼
[tools/import-venue-image.js --venue <id> --image <path>]
      │  Visionモデルで抽出 → Tournamentスキーマに正規化(tools/venue-schedule-vision.js)
      ▼
[tools/tournament-merge.js で安全にupsert]  … 対象店舗以外・過去日には一切触れない、
      │                                        書き込み前に自己チェック、失敗時は書き換えない
      ▼
[data.js へ反映](source: 'semi', verified: false) → サイト反映
```

- 店舗によっては「画像そのものではなく投稿リンクだけ」送ってくることを想定し、
  `--instagram-url` オプションで公式oEmbed(認証不要・ログイン不要)からサムネイルを
  取得する経路も用意してある(`tools/instagram-oembed.js`)。ただし複数画像投稿では
  先頭の1枚しか取れないため、基本は `--image` での直接送付を優先する。
- 実行例: `node tools/import-venue-image.js --venue v40 --image ./inbox/orio-2026-09.jpg`
  (`--dry-run` を付けると `data.js` を書き換えずに抽出結果だけ確認できる)。
- 実行には環境変数 `ANTHROPIC_API_KEY` が必要(Vision抽出用。コードには直書きしない)。
- **既知の制約**: 日程が大幅に変わった月を再取込みすると、前回取り込んだ`source: 'semi'`の
  古いエントリが自動では消えず並存することがある(`tools/tournament-merge.js`のupsertは
  「同じ(date,start)への置き換え」しか行わないため)。再取込み後は表示件数を確認し、
  古いエントリが残っていれば admin.html 側で手動整理すること。

### 半自動パイプライン（LINE / IG 等の埋め合わせ）

完全自動が無理なソースは、**告知テキスト/画像を渡す → LLMで正規化 → `data.js` に追記**で工数を最小化する。
Claude Codeのチャットで人手で行う場合(admin.htmlでの進捗管理)と、`tools/import-venue-image.js` で
CLIから行う場合の両方がこの型に当てはまる。

```
[店舗のLINE/IG告知テキスト・画像]
      │
      ▼
[LLM抽出]  date / start / name / buyin / addon / stack / guarantee / reentry / tags
      │  （下記スキーマに正規化）
      ▼
[レビュー(任意) → data.js へ upsert] → サイト反映
```

各トーナメントは `source`（`auto`/`semi`/`manual`）と `verified` を持つ。

> **⚠ `source` / `verified` はデータ側だけの項目で、現時点では画面に出していない（未実装）。**
> `index.html` にも `tools/venue-schedule.js` にも `t.source` / `t.verified` を読む箇所は無い。
> 実際に画面へ出ている信頼性の表示は **`lowConfidence` の「⚠ 要確認」バッジだけ**（一覧カードと店舗静的ページの両方）。
> なお `verified` は全609件が `false` のままで、「確認済み」を意味する運用も回っていない。
> 取得元のドット表示・「(未確認)」表記は**構想であって実装ではない**ので、実装済みだと誤解しないこと。

### Tournament スキーマ

```js
{
  id, venueId, name,
  date: 'YYYY-MM-DD', start: 'HH:MM',
  buyin: 円, addon: 円|null, stack: 点,
  guarantee: 円|null, reentry: true|'late'|false,
  prize: 文字列|null, tags: [],
  source: 'auto'|'semi'|'manual', verified: boolean,

  // 任意フィールド（無いときはキーごと出さない）
  lowConfidence: true,      // 抽出確度が低く目視確認が要る
  pinnedTags: ['ディープ'], // 人が固定したタグ。自動取込で上書きされず毎回 tags に合流する
}
```

`tags` は**表示に使う最終形**で、自動取込された店舗では毎回
「API由来タグ（`ターボ`/`ディープ`/`PLO`/`ミックス`） ＋ 人手タグ ＋ `pinnedTags`」で組み立て直される。
画面・静的ページの描画は `tags` だけを見ればよい（`pinnedTags` を直接読む必要はない）。

### タグ「大型」の定義

以下の**両方**を満たす場合のみ付与する。1店舗だけで完結する通常営業のトーナメント（各店舗のDAY1サテライト単体を含む）は、大きい大会の予選であっても対象外。

1. 次のいずれか
   - 複数店舗を巻き込んでサテライトが行われている**本線（決勝/本戦）**のトーナメント
   - 大会場を借りて実施する**イベント的な**トーナメント
2. 想定エントリー数が**最低100人以上**

## 法務・信頼性メモ

- フッターでは「当サイトは店舗・主催者が公開している情報を**集約する媒体**であり、賭博行為の勧誘・仲介を行うものではない」「賞品・プライズの取扱いは各店舗・主催者の規定による」と表明する。
  - 2026-07-22に、従来の「当サイトはアミューズメント(賭博性のない娯楽)目的の情報を掲載します」から変更した。
    旧文は**第三者である店舗・主催者のイベントの性質まで当社が保証する断定**になっており、賞金保証のある大型イベント(JOPT等)を掲載すると自社の表記と自社のコンテンツが矛盾するため。
    当社が保証できるのは「当社の立場」までであり、そこに限定する表現に改めた。
- **この文言を掲げる限り、参加受付・予約・エントリー代行・成果報酬型の送客は導入しない。** 導入を検討する場合は、先にフッター表記を見直しレビュー部の確認を通すこと。
  (旧文言が問題になったのは「書いた時点では正しかったが、事業の実態が動いて矛盾した」ため。同じ構造の再発を防ぐ。
  なお定額の店舗PR掲載枠・LINE配信は「広告」であって仲介ではないため、現行の文言と矛盾しない)
- 大型イベント特集ページには、非公式のまとめである旨・情報取得時点・当社の転記誤りの可能性を明示する免責を置く。
  賞金額を掲載する場合は、主催者発表である旨と、主催者側の建て付け(JOPTの場合「プライズは賞金ではなく選手契約」)を併記し、当社が言い換えない。
- **第三者である店舗の許認可状態(風営法の許可の有無等)を、当サイトの声で断定しない。** 店舗自身が公開している言明を載せる場合は「公式サイトによると」等で帰属を明示する。
  - 2026-07-29、行橋の POKER Studio DEEP BLUE の掲載時に定めた。当初は公開noteに「風営法5号許可取得」と当サイトの断定として書いていた。
    許可の有無は公安委員会の処分であって当社に確認手段がなく、誤っていた場合は
    (1)利用者が店舗の法的地位を誤認する (2)保有していない許可を当サイト発で公表された店舗が実害を被る (3)当サイトの正確性が損なわれる、の3方向に影響が出る。
    **当社が保証できるのは「店舗がそう表明していること」まで**という、フッター文言と同じ考え方を店舗情報にも適用する。
- **「県内初」「エリア初」等のNo.1表現も当サイトの断定にしない。** 「〜とされる」「公式サイトが〜を掲げる」と伝聞・引用の形にする。
  - 景表法上の表示主体は原則として供給者(店舗)だが、当社は定額の店舗PR掲載枠を扱うため、将来それと結びついた場合に合理的根拠の議論に接続しうる。先回りして断定を避ける。
- **出典は「どのページの、どの記述か」まで `fukuoka-venues.json` の `note` に記録する。** 店舗公式サイトのトップページ・運営会社の会社概要・第三者媒体では、同じ文言でも重みが異なる。
  - 2026-07-29、DEEP BLUE のレビューで、運営会社の会社概要にある**定款の事業目的**(「風営法５号に準ずる営業及び運営」)を、店舗が許可を保有している根拠と取り違える誤りが起きた
    (実際の根拠は店舗公式サイトのトップページにある店舗自身の言明だった)。**出典URLを列挙するだけでは、次に読む人が同じ取り違えをする。**
- **根拠の弱い情報は、公開面(`data.js` の `note`)でもその旨をヘッジする。** 「住所は未確認。」「住所は第三者情報のため要確認。」等。
  内部の `fukuoka-venues.json` にだけ留保を書いて公開面に落とさないと、読者は確度の差を知らないまま行動する(部屋番号まで載せた住所が誤っていれば、無関係な入居者の部屋を訪ねることになる)。
- **留保付きで載せている値は、構造化データ(JSON-LD)には出さない。** ヘッジは人間が読む文章にしか効かないため、
  同じ値を `LocalBusiness` に入れると、読者には「要確認」と伝えながら Google には確定情報として渡すことになる
  (検索結果に確度の低い住所・電話が事実として出る)。2026-07-30のレビュー指摘で判明し、2026-07-31に是正した。
  - 印は `data.js` の **`"addressUnverified": true` / `"telUnverified": true`**。立っている項目は
    JSON-LD から `streetAddress` / `telephone` を出さない(**表示テキストと `note` のヘッジは今まで通り出す**)。
  - 落とすのは `streetAddress` だけで `address` ブロックごとではない。市区町村・県は `area` / `access`(最寄駅)と
    突き合わせて裏が取れており、`address` は Google が `LocalBusiness` に必須とする項目なので、
    ブロックごと落とすと「不正確な住所」ではなく「住所の無い事業所」になってしまう。
  - `note` が住所/電話の未確認に言及しているのに印が無い店があると、`tools/gen-venue-pages.js` が
    店名を挙げて異常終了する(印の付け忘れは画面を見ても分からないため)。**判定するのは印であって `note` の文面ではない。**
- **Event 構造化データの推奨項目は「裏が取れたものだけ」埋める。** Search Console の
  「`performer` / `offers` / `image` / `organizer` がありません」は Google 自身が**重大ではない問題(＝推奨項目)**
  と位置づけており、欠けてもページや検索機能が失われない。**警告を消すために値を作らない。**
  - `performer`(出演者)は**4ページとも入れない**。ポーカートーナメントに出演者に当たる実体が無く、
    参加者は事前に確定せず出演契約者でもない。主催団体の流用は `organizer` と意味が違うので使わない。
  - `offers.availability` / `offers.validFrom` も入れない。実行日に依存する主張なので静的ページに焼くと必ず陳腐化する。
  - `offers` は**現金だけで入れる金額が一意に定まるときだけ**作る(`cashOffer()`)。チケット併用や
